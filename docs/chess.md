PdfCraft can read a chess book in PDF. It finds the diagrams, reads each one as a position (FEN), and reads the moves in the text, including figurines and annotation signs. It can redraw a diagram, put a lichess link under it, and export the book as HTML, EPUB, Word, RTF, Markdown or PGN. Everything runs on your machine; nothing is sent anywhere.

## What you need

None of these files ship with PdfCraft (fork decisions D2 and D4). Without them, the rest still works.

| File | What it does | Without it |
|---|---|---|
| `chess-pieces.onnx` + `.json` | reads drawn and scanned diagrams | only diagrams set in a chess diagram font are read; the others are found and marked |
| `chess-glyphs.onnx` + `.json` | chess OCR: reads moves, figurines and signs from page images | pages without a usable text layer are listed as needing OCR |
| `text-detection.rten`, `text-recognition.rten` (ocrs) | reads the prose around the notation | the glyph reader reads the prose too, less well |
| a chess diagram font (Chess Merida), or a `pieces` folder of 12 PNG or SVG images | draws redrawn diagrams with real pieces | plain geometric pieces |
| a figurine font (SemFig, or one with the Unicode chess symbols such as DejaVu Sans) | shows the figurines (♘f3) in HTML and EPUB exports | the reader's own fonts |
| ISChess, the Chess Informant symbol font | shows the annotation signs (⩲ ± □ →) in HTML and EPUB exports | the reader's own fonts |

**Where the models come from.** **Chess models…** (the Chess panel's Diagrams tab, the `chess.models` command, or Preferences ▸ Chess models) chooses them:

- **Desktop:** pick the folder that holds them. It is checked at once (each model loaded, not found, or why it couldn't be loaded, such as a `.json` missing beside its `.onnx`) and remembered in the settings (`chess_models`). PdfCraft looks in that folder first, then the folder named by `PDFCRAFT_MODELS`, then a `models` folder beside the executable, then the executable's own folder; the first that holds `chess-pieces.onnx` or `chess-glyphs.onnx` is used. A chosen folder that is gone or holds no model gives way to that search, and Preferences says so (the folder stays chosen, in case a drive is just out). **Check again** reads the folder anew after you replace its files, and a page detected before is then read again with the new model: the readings kept for the session know the piece model by its two files (their SHA-256, taken when it loads), not by its folder alone. **Forget** goes back to the search. A remembered folder that is empty, longer than 4,096 bytes, relative or has a NUL in it is ignored.
- **Web:** there is no folder to look in, so pick the files themselves (several at once: `chess-pieces.onnx`, `chess-pieces.json`, `chess-glyphs.onnx`, `chess-glyphs.json`). Each is read into memory, up to 64 MB a file (the models are about 3 and 9 MB), and the models built from them are used until the page is closed; files with other names are listed and left out, and a model with only one of its two files says which is missing. They are not kept: the browser storage the app has (where the games go) is far too small for them, so the next visit picks them again.

Choosing again while a scan or a reading runs is safe: it finishes with the models it started with, and the next one uses the new ones.

**A model is checked before it is loaded.** A model is a program of sorts, and one that asks for a tensor no machine has used to close PdfCraft the moment its folder was chosen. So its graph is read first and the model is refused, with the reason, when it uses an operation a small image classifier never needs (only convolution, pooling, dense layers, reshaping and the usual activations are taken), holds a subgraph, carries a constant of more than 16 million values, or would make any tensor of more than 268 million values with 1,024 images in (the piece model's largest is half that), or chains more than 256 operations one after another (a run is planned one step per operation, and a chain of 60,000 overflowed the stack; the trained models are about a dozen deep). Once it has loaded, a model with the `chess-pieces.parity.json` or `chess-glyphs.parity.json` its export script wrote beside it (on the web, picked with it) is run on that file's three test images and refused if any probability differs by more than 0.001: its weights are damaged or not the ones exported. A model without that file loads as before.

**A piece model's own gate.** A diagram read by the piece model is accepted without review when it is legal and its weakest square reaches the gate. The gate is 0.80 unless `chess-pieces.json` names another as `accept_min_confidence` (a number above 0 and at most 1; any other value makes the model invalid, and Preferences says why). It is part of the model's calibration: a model that is surer of itself, wrong squares included, needs a higher gate to send as many wrong boards to review. `read_bench --dump=` (in `crates/chessvision`) lists each test board's weakest square, which is what choosing it takes.

**Diagrams** (redrawn on the page, in the editor and in every export) are drawn with the font or image folder named by `PDFCRAFT_CHESS_PIECES`, then a chess diagram font in a `fonts` folder beside the executable (Chess Merida when it is there, else the first by file name, never one whose licence forbids embedding), then an installed Chess Merida, then a `pieces` folder of images beside the executable.

**Chess fonts as piece sets.** Preferences ▸ Chess pieces lists every chess diagram font in that `fonts` folder or installed on the machine whose layout the catalogue has checked, each family once: Merida and Marroquin's other fonts (Cases, Leipzig, Condal, Kingdom, Maya, Mediaeval, Magnetic, Motif, Line, Harlequin, Alfonso-X, Adventurer, Lucena, Millennia), Chess 7, Chess Alpha, the DG cuts (Alpha DG, Condal DG, Kingdom DG, Leipzig DG, which put Alpha's piece letters in a frame of their own), Utrecht, OpenChessFont and ChessBase's DiagramTTF. **Import fonts…** there copies fonts into the `fonts` folder: pick several at once (all of DiagPDF's `Fonts`, say). A diagram font becomes a set; a figurine font (Hastings, Linares, Zurich Figurine…) writes the moves of the exports, below; other fonts, a second copy of a family, and a font whose layout is only presumed (the Linares, Zurich and Hastings *Diagram* subsets taken out of PDFs) are passed over. A font whose licence forbids embedding (Chess Adventurer, Chess Cases) is listed and can be chosen, but is never picked on its own. The `chess_pieces_import` tool does the same from a font file or a folder of fonts. PdfCraft ships none of these fonts: each keeps its own licence. The **analysis board** uses the `pieces` folder first, so a book's diagrams can be in Chess Merida while the board to play on shows your own pictures. A piece folder holds one image per piece, PNG or SVG, named `wK wQ wR wB wN wP bK bQ bR bB bN bP` (`.png` or `.svg`; an SVG wins over a PNG of the same name), each filling one square with a transparent background. Importing a set (a folder of pictures or a saved web page, in Preferences ▸ Chess pieces or by `chess_pieces_import`) over one of the same name, with Replace, swaps the whole set in one step: the new set is written and read back in a folder beside the old one, and only then do the two change places, so a failure on the way (a picture held open by another program or an antivirus, a full disk) leaves the old set whole; a file of yours in that folder that is no piece picture is carried over. A font replaced by **Import fonts…** is written whole beside the old file before it takes its place. `chess_status` lists any folder such a replacement left beside the sets (`piece_leftovers`), which is never offered as a set. An SVG keeps its own paths (a gradient is drawn in its first colour); a PNG is traced into outlines. An SVG nested or chained more than 32 levels deep (groups inside groups, a `<use>` of a `<use>`, a clip path clipped by the next), one that refers back to itself or one that would expand past 200,000 elements is refused with the reason before it is drawn; such a file used to close the app. Either way they draw sharply in the board, the PDF and every export.

**Text fonts** for HTML and EPUB come from the files named by `PDFCRAFT_CHESS_TEXT_FONT` (several separated as in `PATH`), else from the `fonts` folder beside the executable, each for what it draws:

- a figurine font that draws pieces on the letters K Q R B N, such as **SemFig**: each move's piece letters are written in it, and nothing else, so "Kasparov" in the prose stays a word;
- a font with the Unicode chess symbols (DejaVu Sans…): used for those symbols only, so the prose keeps the body font;
- **ISChess**, the Chess Informant symbol font: the annotation signs it draws (⩲ ⩱ ± ∓ +− −+ = ∞ © !? ?! □ △ ⌓ → ↑ ⇄ ⟳ ⨀ ○ ⊕, and the ChessPad signs ⇔ ⇗ ⊞ ⟫ ⟪ ✕ ⊥ ∟ ⯾, the pawn signs and the bishop signs) are written in it; ! ? !! ?? stay plain characters. Read from a book set in it, its letters give the same signs (checked against the font's own drawings, 2026-10-22: `W` is the ring for space and `[` zugzwang's ringed dot, `k` the weak point's cross, never the capture sign; `!`, `∞` over `=`, is compensation, as the user identified it from a book's key, not "good move").

HTML embeds the fonts (the file stays self-contained); an EPUB carries them as files of the book. So a text font must be TrueType or OpenType (`.ttf`, `.otf`) with a licence that allows embedding it: a WOFF or WOFF2 file is not used, since its licence cannot be checked before it is embedded (convert it to TTF or OTF), nor is a font whose licence forbids embedding or allows embedding its bitmaps only; the export tools (`chess_export_html`, `chess_export_epub`…) say why in their reply's `text_font.error`. A diagram font in the same `fonts` folder is for the pieces. A diagram drawn with Merida or cburnett pieces, and a book exported with SemFig or ISChess, carry those fonts into what you export. That is fine for personal use, but not for publishing.

**Reading books set in ISChess.** Quality Chess and Chess Informant books often set their signs, and sometimes their figurines, in ISChess, whose letters stand for something else (`O` is ±, `Q` is +−, `a` is !?, `C` a white knight, `J` a black queen). PdfCraft reads the font by its name, so a page in it reads as the signs and pieces the book prints: `2.Cf3O` in the text layer becomes 2.♘f3 ±, an annotation of the move. The pieces sit on `A`–`L` in White/Black pairs; the other letters are signs, those with a PGN code read as that annotation. No font file is needed for reading.

## In the app

Open the **Chess diagrams** panel (`chess.panel`), or run **Chess ▸ Scan** (`chess.scan`).

### Reviewing a book in 5 steps

1. **Detect diagrams.** Click **Detect diagrams** at the top of the panel. It finds every diagram in the book and reads its position; its ▾ offers the whole book (with its number of pages) or **On this page**. While it runs, the header says **Detecting… page 75 of 703**, and × stops it (the diagrams found so far stay). At the end it sums up: **548 diagrams · 40 to review**. Each open book keeps its own list: detecting in another book never empties this one's, and while another book is being detected, a book with no detection of its own says **Detecting in another book… page 306 of 748** under its header (Detect waits for it).
2. **Review now.** Click **Review now** beside that summary. The first diagram to review opens in the **Diagram** tab beside the page, and the page shows it outlined. The list's chip goes back to **All**, so Page Up and Page Down walk the diagrams to review.
3. **Correct it.** Put the pieces where the book has them: click a square to put the palette's piece there, or use the keyboard (below). The footer says at once whether the position is legal and, when it is not, why (**Not a legal position: Black's king is missing**).
4. **Confirm and next** (Ctrl+Enter). The correction is kept for the diagram, without changing the PDF, and the next diagram to review opens. A reading that was right needs only Ctrl+Enter. After the last one, the tab says **Review done: 40 of 40 checked**.
5. **Export.** **Export book…** (the file icon in the header) writes the book with your corrections. If diagrams are still to review, it asks first: **Review first** or **Export anyway**. When it is done, **Open folder** shows the file.

### Diagram states

Every diagram has a state, shown by its icon and its word, never by colour alone: in the list, on its mark on the page, and in the Diagram tab.

| State | Icon | Colour | Means |
|---|---|---|---|
| **Read** | circle with a check | green | Position read with confidence. |
| **To review** | triangle | amber | Some square was in doubt. Check it before using it. |
| **Not read** | dashed circle | grey | It couldn't be read (a drawn board without the piece model, say). Set the position up in the editor. |
| **With an error** | circle with a cross | red | Reading it failed. It couldn't be read: set the position up in the editor. |
| **Verified** | badge with a check | green | You checked it and kept the reading. |
| **Corrected** | badge with a check | green | You corrected this position. |

A diagram is to review when it was not read, could not be read, or its reading did not pass the reading gate; a repaired reading never passes it.

**Side to move.** In a born-digital PDF the game usually goes on under the diagram with its first move number in bold: **23.** Nf3 means White is to move, **23...** Rxe4 means Black is. The first bold move number under a diagram (in its column, before the next diagram) sets the side to move and the move number in the FEN and the lichess link. A move number in the body font is prose and is passed over. Without one, the side printed in words counts: a caption in the diagram's column just above or below it (`Black to move`, `Pretas jogam e ganham`, `Weiß am Zug`, `White to play and win`, `Mate in 2` says no side), else a heading over the page's diagrams (`Black to move in all positions`; a heading spanning two columns of diagrams, or standing further than a third of a board above the first). Only a short line without moves is read so (at most eight words): a line of moves is a solution, and analysis (`if it were Black to move here…`) says nothing about the diagram. The side's words count where a clause starts, after a label at most (`Diagram 12: White to play`, `No diagrama 64 as brancas jogam`; `It was necessary for Black to play` says nothing), and words prose also uses (`White plays`, `Weiß zieht`) only with a goal after them (`White plays and wins`): a section's title `Black plays …♘d7` names a plan, not the side to move. When the position proves the other side (the side not to move would be in check), the position wins and the reading is flagged. Without any of them, White is assumed, and the exports say the side is not given.

**Mate in n.** When those words ask for a direct mate (`#2`, `Mate in 2`, `Mate em 2`, `Matt in 2 Zügen`; up to three moves), the reading is solved as a chess problem is: every first move that mates in that many moves against any defence (the *key*). Castling is allowed when the king and rook stand where they started (the problem convention), and a key that castles is said; en passant only when the position says so. If the page did not say who plays, the side that mates is to play — only when it is the only one: when both sides mate (every back-rank combination), the side stays assumed and the page's notes say "both sides mate in 1". A position with no mate, or with more than one key (two keys usually mean a misread square), is to review, with the best try and the defence that refutes it. The **Diagram** tab says what was found under the board, while the board shows the position read: "Mate in 2: 1.Qf7! (unique)" (unique only for one key proved), the keys of a cook, or "none found" with the best try and the defence that refutes it; the moves are in SAN as the solver writes them. A helpmate (`h#2`), a selfmate (`s#2`) or "White to play and win" is never solved. The search counts positions, not seconds (200,000 a side, about a fifth of a second at most), so it answers the same on every machine; `chess_mate` solves a FEN headless. A position you set by hand starts the moves under it however its FEN is written: its pieces alone (White to move), or with the `_` of a lichess address.

The colours are theme tokens, in the light and dark themes, and each state's text on its pale fill reads at 4.5:1 or better. The same rule gives the states to the app and to the tools (`pdfcraft_engine::chess::corrections::Status`; `chess_diagram_states` counts them).

### The Diagrams list

- **Chips** filter by state, named as groups with their count (**All (548)**, **Read (468)**, **To review (40)**, **Verified (9)**, **Corrected (12)**, **Not read (20)**, **With an error (8)**; in Portuguese **Todos (548)**, **Lidos (468)**…); one state at a time, plus **On this page**. **Follow the page** keeps the page on screen at the top of the list.
- The list groups the diagrams under their page's header (**Page xvii · 25 of 703**, the printed page number and then the PDF's), which goes to the page; its context menu has **Mark the page as checked**: every diagram of that page read with confidence is kept as Verified, and those to review are left for you (accepting them in bulk is deliberately not offered). The `chess.verify_page` command does it for the page shown. Every place of the chess panels says a page the same way, the printed number when the PDF has page labels, else the page's own (plan A9-T2b): the list, the Diagram tab, the Text tab and its book's games, the classic editor, the question about a draft and the name of a game opened from a diagram ("Diagram 1, p. xvii"), as the exports do.
- A row says **Diagram 1**, its state and, under the pointer, its ⋯ menu: **Open on the board**, **Analyze**, **Copy FEN**, **Open in lichess**. The FEN is in the row's tooltip, not in the row. They all take the position the diagram shows: its correction when you kept one, else its reading, so a diagram no model read can go on the board once corrected, and **Open in lichess** opens the correction.
- Only the rows on screen are built: 2,000 diagrams add about 0.2 ms to a frame.
- An edit of the PDF, Undo or Redo keeps the list: each page read is followed to where its content is now, and only the pages that changed are read again, in the background.
- On the page, each diagram has a mark in its state's colour, with its number on a tab outside the box. A click picks it, with Select or with the Hand (a drag with the Hand only moves the page).

### The Diagram tab

- The header names the diagram by its page (**Page 17 · diagram 1 of 2**, which shows it on the page), and walks the diagrams of the list's chip (with none, those to review) with ‹ › and a counter (**12 of 40 to review**, **3 of 12 · Corrected**). Going round from one end to the other is said (**Back to the first diagram**).
- The board, the palette of pieces (on the light square, with an eraser), **To move**, **Move number** and **Details**: castling written out (**Castling — White: short, long · Black: short, long**; a right the pieces no longer allow is taken off), the FEN, **Flip board** and **Restore the automatic reading**. Squares the reading was unsure of are outlined, each with its second reading one click away (**Change to: White bishop**, or **Empty the square**).
- The footer says at once whether the position is legal and, when it is not, why: **Not a legal position: Black's king is missing** (or two kings, the side not to move in check, a pawn on the first or eighth rank, castling rights the king or rook no longer allows, an en-passant square that does not fit the pawns…). The set-up and the board say why too.
- The footer stays in place: the legality chip, ⋯ (**Redraw in the PDF…**, **Add lichess link**, **Copy FEN**, **Open in lichess**, and **Forget the correction** when one is kept) and **Confirm and next** ▾ **Only confirm**. The way you confirmed last is the one in front next time. With nothing left to review the button is **Confirm**, with no ▾; once the position shown is the one kept, it says **Confirmed**, greyed out, until the position changes.
- **Analyze on the board** (the gauge) puts the position as edited on the board with the engine analysing it.
- **Redraw in the PDF…** keeps the position as the diagram's correction, then draws it over the diagram, as one undo step; the first time, it asks (**Don't show again** is remembered). When the correction can't be kept (a newer PdfCraft's file, which this one only reads), nothing is drawn and the notice says why. Only that page is read again, and the correction follows the page as drawn.
- **Undo a correction.** Confirming (here, or **Confirm correction** asked about a draft), **Forget the correction** and **Mark the page as checked** are each one step of the book's corrections. A notice at the foot of the page says what was done (**Diagram 2, page 13: Corrected**, **…: correction forgotten**) with **Undo**; it stays until your next click or key. Right after, Edit ▸ Undo, Ctrl+Z and the command search undo it ("Undo Confirm correction"), and Redo does it again; a click on the page or in the chess board's panels, a change to the PDF or F6 gives Undo back to the document or the game. Undoing a confirmation leaves the position on the board as changes not confirmed; undoing a Forget brings the correction back, kept as a new revision so that no other copy of the file brings the deletion back. The steps last for the session.
- **Forget the correction** over changes not confirmed yet asks first (**Forget the correction?**), since they go too; Cancel has the keyboard.
- **Unconfirmed changes** are kept as a draft per diagram (a dot on its icon) while you look at others. Closing the document, quitting, exporting or detecting again over drafts asks first: **Confirm correction**, **Discard changes** or **Keep editing**. When the correction can't be kept, the question stays open and says why, every time it is tried, and nothing waiting goes on. A document closed by any way takes its drafts with it.
- Preferences can bring back the editor inside the panel (the classic editor) instead of the tab. **Read mode**, which has no Diagram tab, always uses that editor: picking a diagram there opens it above the Diagrams list, and it confirms as the tab does (**Confirm and next** ▾ **Only confirm**). Leaving Read mode opens no Diagram tab. Ctrl+Enter, Page Up, Page Down and Esc are the tab's keys only.

**Where corrections are kept.** On the desktop, in the app's data folder (`chess/corrections`: `%LOCALAPPDATA%\PdfCraft\chess` on Windows, `~/Library/Application Support/PdfCraft/chess` on macOS, `~/.local/share/pdfcraft/chess` elsewhere, the portable data folder in portable mode), open to your user alone, and the command line and the MCP server keep them there too, so what one corrects the other reads (since plan A9-G5a; before, the app kept them in the recovery folder and the command line in `.pdfcraft` of its working folder). Each start brings in what an earlier PdfCraft kept in the recovery folder's `chess`, merged correction by correction and never copied over, and leaves that folder as it was; an earlier PdfCraft that goes on writing there is brought in again at the next start, and the app says so. One file per book, keyed by the PDF's `/ID`, its path and its name and size, so they survive closing the book, editing it, undoing and saving it under another name; on the web, in the browser's storage. Two different `/ID`s are two books, even at the same path or with the same name and size. Every PDF that PdfCraft made by extracting, splitting or combining pages before plan A9 has one and the same `/ID` (`9BA0D5AA…`); it counts as none, so such a file is known by its path, or its name and size, and a corrections file an earlier build named after that `/ID` is still found by the path it records. A correction is matched to its diagram by its page's content and its place on the page, so a page moved by an insertion still finds it. It also remembers the pages around its own, which tell a page that was edited (the correction stays) from one that took its place when pages were deleted or inserted: then the correction is kept but no longer applied to any diagram (`chess_correction_list` calls it an orphan), so deleting a corrected page never gives its position to the diagram that moves up into the same place. When two corrections are over one diagram, the one whose page was found by its content wins over the one found only by the page number, then the later one; correcting a diagram again, even after its page moved, revises its one correction. A correction takes at most one diagram, the one its box overlaps most: the marks on the page, the list, the editor and Forget follow the very rule the exports apply (plan A9-G2b), so a correction over two overlapping boxes marks only the diagram the exports give it. A diagram's correction wins over a new reading, in the list, the board, the links and every export. The corrections file is of version 2 since plan A9 (G2a): an earlier PdfCraft opened alongside shows none of that book's corrections and refuses to confirm new ones (written by a newer PdfCraft), never rewriting the file; this version reads the earlier files and writes them as version 2 at the next confirmation. Since plan A9 (G3a) a book's corrections file is named `<hash>.corrections.json`, so the book's PGN kept in the same folder never shares its name; the file an earlier build wrote (`<hash>.json`) is still read and its corrections merged in, and it is never written, moved or deleted: an earlier PdfCraft opened alongside keeps working on its own file, and what it confirms is seen here the next time the book is read. It does not see what this version confirmed, unless it is of version 2 and the book has no `<hash>.json`: then it finds the new file by the book it records and changes it there. A correction in the file that can't be read (a box with its corners out of order, a page past any book's) is left out and counted, and the others are kept; the confirmation that writes the file without it first keeps the file as it was beside it (`….bad`). Reading the corrections (opening a book, the reading tools) never renames a file; a file that can't be read at all is reported, and set aside as `….bad` only by the next confirmation, never deleted. Books that earlier builds made by extracting, splitting or combining shared one `/ID`, and one corrections file named by it can hold several books' corrections: each book sees its own in it (found by its pages' content), the book whose path it records lists the other's as another book's (`other_book` in `chess_correction_list`), and the next correction confirmed for a book moves its own into its own file and leaves the others there for their book; reading never splits it, and nothing is deleted. A confirmation holds the folder with the system's file lock (`corrections.flock`), which a PdfCraft that stops lets go of at once, so a lock is never taken over for being old and two writers never change the file together; it takes the lock file earlier builds use (`corrections.lock`) too, inside its own, so they never write beside it (on a folder whose file system has no locks, such as some network shares, that one alone, and the tools say `old_lock_only`). Staging files a PdfCraft that stopped left behind (`<hash>.corrections.json.tmp…`, more than an hour old) are removed by the next confirmation; no other file in the folder is touched. The tools that only read the corrections need only read access to their folder (an MCP server given `--automation-read-root` alone reads them), and a folder that isn't there holds none. Since the corrections are kept unencrypted, nothing is kept for a document that doesn't allow copying, and an encrypted document's only with consent: the tools when told `allow_encrypted`, the app once you say so (plan A9-I1c). The first time the app would keep something of an encrypted document (a correction, its book's PGN, a game, a character sample), it asks once, in a dialog: “Keep your chess work on this protected document?”. **Keep them** writes what waited and keeps the rest from then on; **Don't keep** (or Esc) writes nothing of it. Until you answer, after Don't keep, and always for a document that doesn't allow copying, the work goes on in memory (the diagram stays Corrected, Undo works) until the document is closed. The answer holds for every kind of thing kept, until the document is closed. **On the web** (plan A9-I1b) the browser's storage keeps them under `pdfcraft-chess-corrections-v1`: a value there that can't be read is never written over: the app says so when it starts, keeps it aside as `pdfcraft-chess-corrections-v1.bad` (`.bad2`, … when taken) at its next save, and keeps no correction until then (a confirmation says why); before it writes, it reads what the storage holds now and merges it in, correction by correction, so two tabs never lose each other's corrections and a forgotten one stays forgotten; a value past its 1 MiB is kept whole when read, and a change past it is refused, and said.

**Questions and menus with the keyboard and a screen reader** (plan A9-I11a). Every chess question is a dialog named by its title. It opens with the keyboard on its first button that changes nothing: **Review first**, **Confirm correction**, **Cancel** before a redraw. Tab stays inside it, Esc closes it, and the keyboard goes back to the control it came from. The panel's menus are read as menus; a choice of one among several is read as checked or not. A check box's or radio button's edge reads at 3:1 against the panel. `docs/chess/analise-9/d26-roteiro.md` is the NVDA script, with what it should say at each step.

### The Text tab, exporting and the board

- The **Text** tab shows the page beside it read as a chess document: headings, paragraphs and moves.
  - Moves are coloured by what replaying them found: valid, illegal, not reached, or unchecked.
  - Click a move or a paragraph to see where it is on the page, or click a diagram to edit it. A diagram whose page was not detected yet is detected first, the page of the text whatever page is in view, and opens in the **Diagram** tab once it is found; so does **Keep editing** a draft of another document.
  - **Double-click a move**, or choose **Open this game on the board** in its menu, to open its game on the board at that move. The pages around the page are read for it too, up to four each way, so a game the book runs on from the page before or onto the page after comes whole; a move at the top of a page that goes on from the page before finds its game there. A page that can't be read, or holds none of the game's moves, ends the game there. Each page is walked again from what was read on it, never from what an earlier walk made of it, so the moves come out as a new reading of the pages would give them (a move the reader's c-for-e repair played once is read again as printed).
  - **Read this page with chess OCR** reads the page image instead of its text layer. A picture on the page (a photograph's halftone, a dusty scan) no longer stops the page being read: its fine dots are left out, and a strip with too many of them is skipped and said in the notes, the lines above and below it still read (plan A9-V2).
  - **The book's PGN.** When a `.pgn` sits beside the PDF with its name (emoji, symbols, spaces and case set aside, so `📚Book.pdf` finds `Book.pgn`), the panel offers it, once per document: **Use** or **Not now**, which is remembered. The file's name is in the offer's text, which wraps, and in what a screen reader says for each button. **Load the book's PGN…** picks one by hand. A diagram is in the book's PGN when the PGN has its pieces with its side to move, or only its pieces when White was assumed; the list's state, the diagram's confirmation and a suggestion near it ask this one question the same way. A position you set as its pieces alone counts as White to move, and one written with the `_` of a lichess address is read too. When the PGN confirms a diagram with another side to move, castling or move number, the moves after it are read again from it, so the games, their PGN and the links start where the book's do. `chess_document` says when it did (`reference.walked_again`). On 60 pages of Harikrishna's *Beat the French Defense with 3.Nc3* linked to its PGN (75 diagrams confirmed), valid moves go from 1,070 to 1,087 (18 gained, among them 17 that were not reached; 1 lost, a move of a bracketed comment that only started a game from a diagram whose side the PGN corrects), and linking again, also after a round trip through the JSON, gives the same document. A choice you make on a move in conflict is kept with the move as it was read, so it stays with that move when the moves are read again, and never moves to another move at the same place. It also keeps the PGN's move it was made against. Loading the same PGN again keeps your choices (the same file is known by its bytes too, whatever text a newer reader makes of them), and so does loading **another** PGN: the notice says how many choices name a move the new PGN doesn't have. Those stay kept and apply again with a PGN that has their move, since a choice only counts for a move in conflict with that same move of the PGN. A new reading may cut the page into other blocks (a diagram's own text set apart, a paragraph the layout had cut joined), which moves its moves: a choice is found again by its move, the one of its place among the page's moves printed the same (kept with each choice made since), or, for a choice made before, the only move of the page printed so, else the one at its place. When the Text tab reads a page, the choices made on it are taken to their moves there once and written; a choice found on none is kept, never put on another move, and the Text tab says how many (**Choices made on this page not found in its reading (kept): 2**). `chess_document` says so too (`reference_kept.decisions_found`, `decisions_unmatched`).
  - **Where the book's PGN is kept.** As the corrections are (plans A9-G3a, G5a): in the app's data folder (`chess/reference`, shared with the command line; what the recovery folder kept before is brought in) on the desktop, in the browser's storage on the web, one file per book, now `<hash>.reference.json` (format version 2), so the book's corrections in the same folder never share its name or are taken for it. The file an earlier build wrote (`<hash>.json`) is still read: the PGN kept or removed the latest wins, and with the same PGN on both sides the choices made in each are kept (this version's where both chose on one move); it is never written, moved or deleted. An earlier PdfCraft opened alongside keeps to its own file: it doesn't see a PGN loaded, a choice made or a removal done in this version, and what it loads later is seen here. Removing the book's PGN now leaves its file, saying when the PGN was removed, so the earlier file, older, doesn't bring it back. Reading it never renames a file: a file that can't be read is said, and kept aside as `….bad` by the next change, which says so; a choice in it that can't be read is left out, the PGN and the other choices kept. Fields a later build of version 2 writes are kept as they are. The file says the reading of the build that wrote it (`reader_version`); a file a later reading wrote, whose places and ordinals are that reading's, is only read here, and none of its choices is applied. Changes hold the folder with `reference.flock`, as the corrections do with theirs; the tools that only read it need only read access, and the tools keep a PGN for an encrypted document only with `allow_encrypted`, and the app only once you say so (the one question about the document, above), never for one that doesn't allow copying. On the web it is kept as the corrections are (`pdfcraft-chess-reference-v1`, 2 MiB): kept aside when it can't be read, merged with another tab's before writing. A PGN picked in the browser is read only up to the 64 MiB a book's PGN may have, its size looked at first, and a file the browser refuses to read is said; **Open PGN…** reads its files the same way (32 MiB each).
  - **Book origin** says where the book's pages came from, for the open document: **Auto** decides page by page, **Born digital** never uses chess OCR (a page whose layer looks poor is read as it is, with a note), and **Scanned** reads every page, and every export, with chess OCR.
- **Export book…** (the file icon in the panel's header, or the Text tab) writes the whole book as PGN, EPUB, HTML, Word, RTF or Markdown, with your corrections. With diagrams still to review it asks first (**Diagrams not checked yet: 40**, **Review first** or **Export anyway**); when it is done, a window says where it wrote the file, with what the export noted (a page named as the book numbers it, as the file does), and **Open folder** shows it. **Diagrams as PGN games**, in the same menu, chooses which diagrams the PGN gives a game of their own (only those not in a game, all of them, or none), with the book's PGN loaded too: there, after the PGN's games, and "not in a game" means linked to no move of it. The PGN is written as every PGN PdfCraft writes (plan A9-F4): lines of at most 79 characters (a word longer than that alone on its line), the figurines of the book's text in the comments as letters (`Nf3`), a comment printed after a move's variations right before the next move. Markdown's diagram images go in a folder beside the file. The Markdown links them with each name of the folder percent-encoded, so a file named `Livro #2 100%.md` finds them, and the text reads as printed: `&copy;` stays `&copy;`, a paragraph `---` stays three dashes (plan A9-X1a). HTML and EPUB drop the characters XML does not take (U+FFFE, U+FFFF and the other noncharacters), and an EPUB or Word file that would pass what a zip file holds (4 GB, 65,535 files) is refused with an error instead of written broken. The lichess address under a diagram is a working link in every format (a real hyperlink in Word and RTF). An EPUB's cover is the book's first page, drawn at most 1600 pixels on its long side; when it cannot be drawn, the book has no cover and the export says so. An EPUB of some of the pages has an identifier of its own (the PDF's, followed by the pages, `…:pages:2-4,7`), so a reader keeps two parts of one PDF apart. For a reader who listens (plan A9-X3): an annotation sign is said by its name, and a figurine by its piece and the side that moved, in the book's language (`±` is *As brancas estão claramente melhor* and `♞` on a White move *Cavalo branco* in a Portuguese book) — the interface's own names, in Portuguese, Spanish, French, German, Italian, Russian and Polish; in any other language, Dutch included, in English, and the file says so; Word and RTF print a sign's name in brackets after it (not after `!` or `?`); a diagram exported as FEN has its position in words beside it; and the review highlight, when it is on, also underlines what to check and says it to a screen reader with the reason a move has (*A revisar: Lance ilegal*); an EPUB titles each page with the book and the page as the book numbers it (`Book — Page 13`), nests its table of contents by heading level, says how it can be read from what it holds (how many diagrams are described and name the side to move, and whether the page numbers are the book's own; in English), and leaves out an author named *Unknown*. The book is read once per session: an export, **Align the book to the PGN** and the Text tab's reading start from what **Detect diagrams** (or an earlier export) read for the document as it is, with the same models folder, and what they read is kept for the next one; after an edit, only the pages it changed are read again (plan A9, G11).
- The **Chess board** is an analysis board in its own tab, beside the Inspector.
  - **Double-click a diagram** on the page, or choose **Open on the board** in the list or the editor, to load its position. The position being edited is used when the editor has that diagram. The moves under the diagram give it its side to move and move number (`12...e5` makes it Black to move at 12): its page is read for them if the Text tab hadn't read it, and they are applied as long as you haven't moved yet.
  - Play moves by clicking a piece and then where it goes, or by dragging it. A pawn reaching the last rank asks for its piece.
  - The arrows, or the arrow keys, Home and End with the pointer over the panel, walk the line. A move made at an earlier point starts a **variation**; forward follows each move's main reply, as on lichess.
  - The move list shows variations in brackets and comments in italics. Click a move to go to it; right-click it to **make it the main line** or **delete from this move**. A line that would push the old main line deeper than variations nest is left as it is, and the board says so ("Not done: variations would nest too deep."), from the move's menu and from **New main line** alike.
  - The move shown takes annotation glyphs (`!`, `?`, `!!`, `??`, `!?`, `?!` and the evaluations) and a comment.
  - **Game details** holds the players, event, site, date, round and result, written as the PGN's tags.
  - Before the first move, choose who is to move. **Flip board** shows it from Black's side.
  - The **FEN** and **PGN** fields follow the board. Edit one and press Enter (FEN) or **Load PGN** to load it. Enter with the FEN as shown does nothing; a FEN typed while the game has moves asks first: **New game with this position** (the choice Enter takes; the game keeps its moves) or **Replace this game**. **Standard start position** (in the FEN section) is a new game too when the game has moves. Text typed in the PGN field stays as typed while you move on the board, marked **PGN edited** with **Load** and **Discard**; loading the same game again (an edited comment or variation) keeps the move shown and where its moves are on the page. Deleting moves is a command of a move's menu (right-click), not a button beside the list. A PGN's variations, comments, glyphs and tags are read; a move that can't be played ends only its own line, and the first one is named with why: not a legal move there, more than one legal move written so, or the game already holding 10,000 moves. A variation never takes the main line's place: one that starts by repeating the main line's move (`2. Nf3 (2. Nf3 Nc6 3. Bc4) 2... Nc6 3. Bb5`) adds its moves as variations where the main line goes on (`3. Bb5 (3. Bc4)`). A comment between a variation's `)` and the next move is that move's comment-before, and a variation holding only a comment leaves it on the move it was an alternative to. Spellings books and sites use are read rather than stopping the game: `e8Q` and `a8=q`, `e.p.` after a capture, `…` in move numbers, `±`, `+-` or `∞` alone or glued to a move (`Nf3±`); `1/2`, `½-½` and `0.5-0.5` are a draw, and a result with no move before it is kept. The `Result` read is the game's and is written back as read, `*` included: the board never writes over it (a mate or a stalemate at the end of the main line that disagrees with it is counted in the notice and listed by the tools, `result_mismatch`); a game made on the board, with no result set, takes the board's (mate or stalemate), and fifty moves without a capture or a pawn move decide nothing, since that draw is claimed. A game of another variant (its `Variant` tag: Chess960, Crazyhouse…) is refused whole, with its name, never read as chess and cut at its first move chess has not; `Standard` and `From Position` are chess. Castling is read with the Cyrillic O a Russian keyboard or OCR gives (`О-О`), and a promotion only as a pawn's onto the last rank (`Nf4=Q` is no move). Nothing is cut or dropped unsaid: a comment keeps up to 64 KiB, read or edited alike (a field says so under it past that), a tag 256 bytes and a game 64 tags, a move 8 glyphs side by side whatever their group; what passes a limit, a glyph with no move before it, a result the `Result` tag disagrees with and a `FEN` made legal (castling rights the pieces don't allow, an en-passant square no double step left, a clock past 100, move 0 or past 999) are counted in the notice ("Read with changes"), and the tools list each. The rest of a line after a move that can't be played is kept as a comment where its reading stopped, so saving the game loses none of its text. With several games in the PGN field, the first goes on the board and the others are added to the document's games after the rest (at most 256 in all, as **Open PGN…** reads a file); a notice says how many, and Undo takes the games added back before the game loaded.
  - A diagram whose position is not legal is shown in a red frame and cannot be played until it is corrected in the editor.
  - Under the board, whose move it is (**White to move**, after a dot of that side's colour), in check or not, is in the text colour: red is only for a position that is not legal and for mate. A screen reader hears the board as **Board, White to move, move 7**, with its pieces in words in the interface's letters (**White: Kg1, Qf3; pawns a2, b2. Black: Kg8; pawns g7.**), never its FEN.
  - **Draw on the board** with the right button, as on lichess: a click circles a square, a drag draws an arrow. Hold Shift for red, Alt for blue or Ctrl for yellow; green otherwise. Drawing the same thing again takes it off. Drawings belong to the move shown, so they come back when you return to it, and each one is an undo step. They are written into the PGN in the move's comment, in the convention ChessBase and lichess use: `{[%csl Gd5][%cal Rg1f3] the rest of the comment}` (squares, then arrows; G, R, Y and B for green, red, yellow and blue). A PGN with them shows them on the board, and the rest of its comment, other `[%…]` commands such as `[%clk]` and `[%eval]` included, is kept. An entry the board can't draw (another colour letter, a square that is not one, more than 64 on a move) stays in the comment as text. Moving a piece leaves the drawings; **Clear drawings** in the Analysis section takes them off the move shown. A position that is not legal has no game, so its drawings are kept beside it and not written anywhere.
- The board is also the **study board**, with more for studying a position (the Chess panel's tabs are **Diagrams** and **Text**). **Open on the board** in the list or the editor loads a diagram there and brings the board forward, docked or in its own window.
  - **Set up a position**, a tool of the rail beside the board, puts the set-up in the board's place, with pieces from a palette: click a square to put the chosen piece there, click it again or right-click it to empty it. **Standard start position** and **Empty board** start over; set who is to move and the castling rights (a right the pieces no longer allow is taken off). The panel says at once whether the position is legal, and **Done** plays from it (one undo step). When the game on the board has moves, the choice is **New game from this position** (a new game after it in the list; the game keeps its moves) or **Replace this game** (its moves go, told with Undo). **Cancel**, Esc, another tool or another game leaves the set-up.
  - The **Analysis** section under the board, closed until you open it, holds the rest. **Engine analysis** runs a UCI chess engine you installed, such as Stockfish. None comes with PdfCraft. It is found through the `PDFCRAFT_CHESS_ENGINE` environment variable (the program's path) or the program in an `engine` folder beside PdfCraft — in the folder itself or in a folder inside it, as it comes out of its download (`engine/stockfish/stockfish.exe`) — or you pick one with **Choose engine…**. The program you pick, the number of lines and whether analysis is on are remembered in the settings (`chess_engine`) for the next session. A remembered program that is no longer there is ignored, and the engine is looked for again.
    - It analyses the position shown, to depth 30, and starts again whenever the position changes. It stops while the board is not shown (another tab in front of it, the panel closed, Home), docked or in its own window, and goes on when it is back.
    - Back on a position it had analysed this session (one of the last 64), the lines it found are shown at once and it searches on, showing them until it goes deeper; a position already analysed to depth 30 is not analysed again. Changing the number of lines starts afresh.
    - A thin **evaluation bar** beside the board shows who is better, and the best move is drawn as a blue arrow. On a mated position (the engine's `mate 0`) the bar is all the winner's and the score reads `#`.
    - **Lines** (1–3) shows the engine's best lines with their scores for White (`+0.40`, `#3`). Click a move of a line to play the line up to it; moves already in the game are followed, the others start a variation.
    - **Analyze**, one click in a Diagrams list row's menu, the Diagram tab or the board's title, puts the position on the board with the engine analysing it and this section open. With no engine installed, it says how to get one: **Choose engine…**, **Open stockfishchess.org** (the download page, in your browser) or **Not now**; or put the program in an `engine` folder beside PdfCraft (the folder it was unpacked into may go straight in there).
    - The engine runs as a separate program and only on the desktop. No automation tool starts it.
  - The section also shows the **material** each side is ahead by, as pieces and points, clears the drawings and says how they are drawn.

## PGN toolbar

The **PGN toolbar** turns a book's printed moves into games without playing them one by one: you select the text on the page and it goes into the game on the board, as the line, a variation or a comment, with its glyphs. A narrow rail of tools beside the board does the rest: glyphs, comments, the shape of the variations, the games of the document, and the board in its own window. (Its spec is `plan/chess/pgn-toolbar.md`, steps T1–T16; it is local to the fork.)

| **Glyph brush** | B | Armed, each move clicked in the notation gets the brush's glyph, or loses it. |
| **Move comment** | Enter | Opens the comment editor, with the comment before the move. |
| **Glyph palette** | G | A floating window of figurines, glyphs and `½ – × † ‡`: a glyph goes on the move, the rest into a comment or field. |
| **Follow** | F | The page follows the move shown (below). |
| **Show in PDF** | | Scrolls the page to where the move shown was printed. |
| **Undo**, **Redo** | Ctrl+Z, Ctrl+Shift+Z | The game's own history (below); the names say what they would undo. |
| **Chess in its own window** | | The board and the Chess panel in a window of their own (desktop only). |

On macOS, Ctrl is ⌘ and Alt is ⌥. Every tool is also a command (`chess.tool.*`, `chess.variation.*`, `chess.moves.*`, `chess.nag.1`–`6`, `chess.comment.edit`, `chess.palette.toggle`, `chess.source.*`, `chess.window.detach`), so it can be found with Ctrl+K and run by automation. A move's right-click menu in the notation has the structure tools, each saying what it would act on (or why it can't), and, where one could act on several variations on the way to the move, those variations listed under it, nearest first ("Promote one level: 2…Nc6 · 1…c5"); then the move-quality glyphs and the evaluations, ticked while the move has them, and **Remove all glyphs**, which act on that move without going to it; then **Diagram here**, **Copy line with figurines**, **Copy line (letters)**, **Delete from this move** and **New game from this position**.

**The chess key scope.** The scope follows the keyboard focus. A control of the chess board's panels with the focus (the Board panel, the Move list, the Chess panel, the chess window, the glyph palette), or a click there or a change to the game while no other control has the focus, gives the keyboard and Undo to the game. Tab to a control anywhere else, **F6**, a click on the page or in another panel (Tools, the Inspector's other panels, the Diagram tab, which has keys of its own), or a change to the document gives them back to the document. A menu, a popup or a dialog opened over the window changes nothing. While the game has them, the keys above go to the board before anything else sees them: Delete deletes a variation, never a page or an annotation, and the arrows walk the game, never the page. They are left alone while a text field has the keyboard (a letter or Delete typed in a comment is the comment's), while a menu or popup is open, under a dialog, and while a control outside the chess panels has the keyboard: a divider between the panels keeps its arrows.

**One-key shortcuts.** **Preferences ▸ One-key shortcuts (B, C, F, G, O, X, signs)** turns the letters, Shift with a group's letter and the typed signs off (WCAG 2.1.4); the control channel's `one-key-shortcuts` and `typed-wait` set it and the wait below, and both are kept with the preferences. A key the control channel sends (`ui key`) reaches the chess panels as a pressed one does (plan A9-Q5), and `ui inspect` says what a screen reader is told besides the name: `live`, `modal`, `expanded`, `has_popup` and `active_descendant` (the editor board's square under its cursor), so an agent can walk the keyboard journeys of the installed app. The rail's buttons and the command search do the same things, and the buttons' names and the command search stop offering the letters. Every key the chess panels take is in one key map, made from the rail, moving about the game, the typed signs, the Diagram tab's keys and the app's own letters (V, H). A test refuses a key with two meanings: a letter or a sign means one thing in every chess panel, while Esc, Page Up and Page Down act on the place the keyboard is in. The shortcut sheet is to be F1 (`?` is the "poor move" sign typed), and the Diagram tab's Original / Read switch Alt+O (O alone is the OCR area).

### Capturing text

- **Arm a tool.** **Capture** (X) or **Capture as a comment** (C). The page tool switches to Select and a chip in the page's corner says what is armed ("Capturing · automatic ▾ · Esc to stop"); its menu switches the mode, and Esc stops.
  - **Automatic** reads the text as the book sets it: a bold first move continues the main line, anything else becomes a variation where its move numbers fit; prose becomes comments, brackets variations, and `!`, `±`… glyphs.
  - **Forced** modes (Shift+X steps through them) are for books that use no bold, or text that fits in more than one place: **as the line** continues the line of the move shown (a different move already there becomes a variation), **as a variation** of the main line, **as a sub-variation** of the line of the move shown or one outside it.
  - **Comment** puts the text on the move shown, its moves in English SAN. The chip's switches put it **before** the move instead of after, and **replace** the comment instead of adding to it.
- **Select the text and let go.** The selection grows to whole moves ("20.Nx" takes "20.Nxf6+"). It is read from the page's glyphs, not from copied text: a figurine font's pieces are pieces, and a bold glyph is bold. The language is the document's (as the **Text** tab read the page; English until it has), never guessed from the selection: `Rc7` is a rook in English and a king in Portuguese.
- **Without arming anything:** **Send to PGN ▸** in the bar beside a selection, or in the page's right-click menu, captures it in the mode you pick. **Paste:** Ctrl+V with the chess scope on (and no field typing) captures the clipboard's text; **Paste as ▸** in the board panel picks the mode. Ctrl+C on the page captures too when you turn on **Also capture what is copied** in the chip's menu (off by default).

**Where a capture goes.** The selection's first move decides, by its printed number:

1. The number says the half-move the move is played at, counted from the diagram's move number (a diagram already carries the number printed under it).
2. The candidate lines are the line of the move shown, the line that one branched from, and so on out to the main line. As the line or a sub-variation every one is tried, the innermost first; as a variation, only the main line. Automatic capture takes a bold first move as the main line's continuation and anything else as a sub-variation.
3. On each line the place is the move after which that half-move comes. A first move printed without a number goes after the move shown.
4. As the line, a new move where a move already has replies becomes the first reply, and the old first reply a variation. As a variation, it goes after the replies there. A reply that is already there is followed, not added twice.
5. Each place is tried on a copy of the game: the selection is read from that position and grafted there. The place that plays the most moves wins, then the one with the fewest moves that did not play, then the inner line. Two places that play as many are **ambiguous**.
6. **Renumber** is a choice of its own, not a place. When the first number names no place where a move without a number would go (after the move shown; as a variation, also as an alternative to it), the text is read from there as if its numbers had been printed for it: every number moves by the same amount, and the moves take the game's numbers (`12.Raxe1` after 19…Kh7 is played as 20.Raxe1). In a game with no moves whose start says move 1 (the number under the diagram was not read), the start takes the text's number instead. It is never chosen over a place that plays a move, never makes a place ambiguous, and never goes in without the preview.

**When it asks first.** A capture goes in at once, as one undo step, only when the whole text was read, it fits one place, that place is on the line of the move shown, no line's end was extended by a variation, no move already there was demoted and nothing was renumbered. Otherwise a **preview** opens beside the selection and says why:

| Reason | Means |
|---|---|
| ambiguous | another place plays as many moves |
| incomplete | part of the text was not read: a move that did not play, a bracket that did not balance, text after a result, a glyph or comment with no place, or a comment too long |
| outer line | the place is on a line outside the one of the move shown |
| tip extension | taken as a variation, it found no move to be an alternative to and extended a line's end |
| renumber | the start is renumbered to the text's first move, or the text's moves take the game's numbers |
| implied close | a closing bracket the text lacks was assumed |
| demotes | a move already there became a variation |
| no fit | no place plays a move |
| too long | over 64 KiB of text; nothing was read |

The preview shows where the text goes ("Variation of 18…Qxe1"), **Insert in** to pick another place it fits, **Renumber** when the numbers can be made to agree (switched on it shows the text played that way and what changes, "19...Kh8 is played as 20...Kh8"; switched off, the place chosen before; a correction or another language keeps it), the **Piece letters** it is read with (changing them reads the text again, and becomes the document's language for captures), and the moves as chips: ✓ played, ✗ where it stopped and why, grey not read, bold for the main line. **Apply** (Enter), **Apply and keep the rest as a comment** (what was not read is never thrown away) or **Cancel** (Esc). It follows the page as it scrolls and closes when the document is edited.

**Undo.** A capture is one step of the game's history: Ctrl+Z takes it back even with the pointer still on the page, and the document is never touched. After a capture a notice says what it did ("Variation of 18…Qxe1 · moves: 4") with **Undo**, which stays until the game changes again (it has no timeout), and the new moves are tinted in the move list for a moment (a plain tint with reduced motion).

**Captured text on the page.** Every captured move remembers where it was printed. **Underline captured text on the page**, in the board panel, underlines them, so you can see what is left to transcribe; the places come back with the games in the next session.

A document that doesn't allow copying doesn't allow capturing either. At most 64 KiB of text is captured at once; a selection over 4 KiB is planned off the interface thread.

### Correcting a move that did not play

In the preview, a ✗ chip (a move that could not be played where it was read, or where the graft stopped) is a button: it opens a panel under the chips (step T10).

- **Legal moves near it**: what the legality repair makes of the move in the position it was to be played in: the one reading it settles on, the moves an ambiguous reading fits (`Rd1`: `Rad1`, `Rhd1`), or the three closest legal moves. They are written in the language the text is read in and are **never applied until you click one** (guessing a move goes wrong). A move after one that stopped was never reached, so it has none: correct the first one first.
- **Correction**: a field holding the move as printed, with the **Glyph palette** (the rail's characters plus the ellipsis) inserting at its cursor; Enter or **Read again** takes it. The board panel's floating glyph palette (G) types into it too while it has the keyboard, a figurine or a glyph's sign alike, instead of annotating the move shown, and so do the rail's glyph buttons (on even before the game has a move).
- **The OCR's readings** (text from the OCR area of a scan): the move's characters, a doubtful one underlined (its top two readings within a margin of 0.5); a click lists the reader's top three readings, and picking one puts it in place of the character.

Each correction rewrites the move where it was printed (the page's glyphs keep their place and weight) and reads the whole text again, so the preview shows what the corrected text reads as; nothing goes into the game until **Apply**. A correction that fits nowhere is refused and the text stays as it was.

**Collecting corrected characters for retraining** (step T11, opt-in, desktop only). With **Collect corrected characters for retraining** on in the capture chip's menu, and a folder chosen there, each character of an OCR area that you correct (a reading picked, or a corrected move whose characters keep their boxes) is saved as a 32 × 32 gray picture in `<folder>/<character>/<confidence>_<document>_p<page>_<n>.png`, the layout of ChessVisionOFF's review queue (`revisao_ocr`): the folder is the character's class name there (`digit_3`, `upper_N`, `sym_9812` for ♔), and the name starts with the model's confidence in thousandths, so the most doubtful come first. Nothing is overwritten, at most 2,000 are saved a session, an encrypted document's wait for the one question about keeping its chess (declined, nothing of it is saved), and nothing is trained in the app or leaves the computer.

### Glyphs

PdfCraft knows every glyph of the PGN standard (codes 1–139) and of the extension the public table of non-standard NAGs attributes to the ChessPad editor (140–146 and 238–255): 164 codes, most of them in White/Black pairs, as one table (`pdfcraft_chess::nag::NAGS`). The 28 that books use most are in three groups on the rail, each named for its meaning ("Good move", "White is slightly better"), never read out as a sign:

- **Move glyphs:** `!` `?` `!!` `??` `!?` `?!`, only move `□`, novelty `N`. A move has at most one; another replaces it.
- **Evaluation glyphs:** `=` `∞` `⩲` `⩱` `±` `∓` `+−` `−+` and compensation. At most one; another replaces it.
- **Other glyphs:** zugzwang, development, initiative, attack, counterplay, time trouble, with the idea, aimed against, better is, worse is, editorial comment. These add up.

A glyph goes on the move shown with the code for the side it speaks of (zugzwang: the side to move after it); clicking a glyph the move has takes it off. Each change is one undo step.

- **Typed glyphs:** with the chess scope on and no field typing, type the sign: `!` `?` `!!` `??` `!?` `?!` `=` `+=` `=+` `+/-` `-/+` `+-` `-+` `~`, or `0` to take the move's glyphs off. They come as text, so any keyboard layout works. A sign that a longer one starts with (`!`, `?`, `+`) waits for its next character as long as **Preferences ▸ A typed sign waits for its next character** says: 0.6 s (the default), 1 s, 1.5 s, 2 s or **Until Enter**. Enter puts it on at once, Esc drops it, and any other chess key puts it on before it acts.
- **Glyph brush** (B): each move clicked in the notation gets the brush's glyph, or loses it, one undo step a click; the move shown does not change. A glyph chosen in a group while it is armed becomes the brush's. Esc puts it down.
- **Glyph palette** (G, or the rail's button): a small window floating beside the rail, in the main window or the chess window, that can be dragged anywhere within it and opens again where it was left (for the session). It has the figurines and `½ – × † ‡`, then the glyphs in the rail's three groups (the move row with ChessPad's equivalent move `==` too), a row of **Positional glyphs**, and **More assessments**, all ticked while the move shown has them. A glyph clicked goes on the move shown, or comes off it, as on the rail; the other characters go at the end of the move's comment. While a field had the keyboard (a comment, FEN, PGN, a capture's correction field), any character, a glyph's sign too, is typed at its cursor instead; the rail's glyph buttons do the same then. An assessment without a sign always goes on the move. A click in the palette keeps the keys on the game, as a click in the panel does. Esc, its close button or G closes it.
  - **Positional glyphs**: space `○`, and ChessPad's play along the file `⇔`, along the diagonal `⇗`, in the center `⊞`, on the kingside `⟫` and the queenside `⟪`, weak point `✕`, endgame `⊥`, connected, isolated, doubled and passed pawns `⯺ ⯻ ⯼ ⯽`, the pair of bishops, bishops of opposite colors and of the same color, with `∟` and without `⯾`. ChessPad's space advantage (`$238`) is drawn `○` like the standard's (`$26`), which is the one read in text.
  - **More assessments** (folded at first): the assessments the PGN standard numbers but books write out in words, in a list that scrolls in the room left in the window (the palette never runs past the window's bottom, and moves up when the list opens too low to have room), by name, in sections (move quality, evaluation, initiative and time, space and control, king safety, pawns, pieces, phases of the game), or narrowed by the **Filter assessments** field (by name, in English or the interface language, or by `$n`). One clicked goes on the move with the code of the side that made it, even while a field had the keyboard (as text it would only be `$n`), one undo step. PGN writes them as `$n`, and nothing in a text is read as one.
- **A move's menu** (right-click in the notation) has the move-quality glyphs, the evaluations and **Remove all glyphs** for that move, one undo step each. Only these: the other glyphs are on the rail and in the palette, and a menu with all of them would be a wall.
- **In the notation**, a glyph reads after its move: as its sign where the interface fonts draw it (`⩲` `⩱` as `+=` `=+` and `⨁` as `⊕` where they don't), painted where no bundled font has the sign (`⌓`, `⇗`, `⯺ ⯻ ⯼ ⯽`, `∟ ⯾`, and the bishop signs, which have no Unicode character), and an assessment without a sign by its name, small and muted, with its `$n` as the tooltip: a reader learns nothing from `$24`, and these are rare enough for the words not to crowd the moves. PGN and copied text keep the real character, or `$n`.
- **Diagram here**, in a move's menu, shows a small board after the move in the notation and is kept in the PGN as `$220` (a de-facto code, from the public table of non-standard NAGs; other programs may not read it).

**Reading the signs in books.** The new signs are read in a book's text and after a move as the old ones are: `○` (space, `$26`/`$27` by the side that moved), `⇔ ⇗ ⊞ ⟫ ⟪ ✕ ⊥ ∟ ⯺ ⯻ ⯼ ⯽ ⯾` and `==`. Signs close to others are kept apart on purpose: `=` is still equality (`$10`) and `==` one sign (`$144`), never two `=`, while a promotion (`e8=Q`) is the move's own text; `⇔` (a file) is not counterplay (`⇆`, `⇄`); the weak point's `✕` (U+2715) is not the capture sign `×`; and `⯹`, the Unicode sign for compensation, reads as `©`. The bishop signs have no Unicode character: in text they are the stand-ins the ISChess font's letters are read as (`⧉` the pair, `□■` opposite colors, `■■` the same color), read only glued after a move, as `■` turns up in the text of OCR'd diagrams (62 times in one of the 13 books scanned, never as a sign). Re-reading the ten stored book stretches before and after (2026-10-22, `pdfcraft-cli` `chess_document`, then `examples/walk_bench.rs` and `examples/fragment_bench.rs`) gave the same 2,841 valid moves, every move with the same status, and the same 324 of 333 variations reproduced; the whole text layers of 13 books (about 11.2 million characters) hold none of the new one-character signs, and `==` only in OCR'd rule lines (`====`), which were noise before as well.

### Comments before and after

Under the notation the move shown has its comment, the one after it. **Move comment** (Enter) opens the editor with the **comment before** the move too. Typing in a comment is one undo step per visit to the field, not one per key.

PGN has two places for a comment before a move: after the `(` of a variation the move starts (`(18... {Better is} Qd8 …)`), and after the variations of the move before (`18. Nf3 (18. Nc3 Bb4) {Back to the game:} 18... Qd8`), where ChessBase writes its text before a move. Before a move that continues its line with no variation before it, the PGN writes it into the comment after the previous move (or before the game's first move), and the editor says so. PdfCraft keeps it on its move in the game and in the autosave, so it comes back where it was; only a PGN file loses where it was.

### Structure

Each operation is one undo step, and can be undone exactly: promote one level then demote, or move up then move down, gives back the same tree, comments before included.

- **Promote one level** (Ctrl+↑): the variation continues the line it branches from, and that line's move becomes its first variation; the other variations keep their order. From a move inside a variation, the nearest variation that can be promoted is the one; when several could be, the group's popup lists them by their first move.
- **Make this the main line** (Ctrl+Shift+↑): promote all the way.
- **Demote** (Ctrl+↓): a move that continues its line becomes the first variation, and the variation that was first continues the line instead; the inverse of promoting.
- **Move variation up / down** (Alt+↑ / Alt+↓): among the variations at the same fork. The line itself never moves.
- **Delete variation** (Delete): the variation and its moves; the move shown goes back to the fork.
- **Cut after this move** (Shift+Delete): every move after the move shown, variations included.

Whatever takes moves out of the game (these tools, a move's menu, the button under the notation, a position put in the game's place) is told in a strip at the top of the panel, "5 moves deleted (2 variations)", with **Undo**; the notice stays until the game changes again or it is dismissed (✕). Backspace only goes back a move: it deletes nothing. The game as it was also goes into the document's trash, kept with the autosave (the newest 30, each up to 256 KB). It goes there with the step that took the moves, whichever panel is showing: a move deleted from the move list beside the page counts, and so does a PGN loaded from the field over a game whose moves it doesn't have, even a longer one. Moves that only change places among the variations don't count. The moves can come back after Undo is gone, in a later session too: **Deleted moves (n)…** under the list of games lists them, newest first, and **Open as a new game** puts one after the game shown.
- **Threat (null move)**: the side to move passes, and the moves after show what the other side threatens, as books do (`12... --`). Written `--` in PGN and read back (also as `Z0` or `0000`); refused when the side to move is in check.
- **Copy line with figurines / (letters)** in a move's menu copies the line up to it as book text (`18.♘d5! ♕xe1 19.♘xe7+`), from the start of its variation or of the game.

### Undo

The game has its own history, apart from the document's: every change (a move, a capture, a glyph, a comment, a drawing, a structure change, the game's details, a position or a PGN loaded) is one step, and walking the moves is not a change. Undo and Redo follow the chess key scope (above): with the keyboard focus in the chess panels, or after a click there or a change to the game, they undo the game; with the focus elsewhere, or after a click on the page or in another panel or a document edit, the document. The rail's Undo and Redo always undo the game. The history keeps at most 200 steps and 64 MiB per game, the oldest going first. It is not kept across sessions.

### Games of a document

Every open document has its own games, and the board shows the active one; switching documents switches games. **Games in this document**, in the board panels, lists them by their players, else their event, the diagram they came from, or their number.

- A diagram opened on the board is a **new game**: it never replaces a game you changed (the same untouched diagram opened twice shows its game again). While you don't change it, it is a passing game. The next diagram you open takes its place, with no step of its own: Undo of “Load the diagram” takes the newest one out. It doesn't count toward the 256 games, and it isn't autosaved, since it opens again from its diagram. Change it (a move, a comment, the board turned) and it is a game like any other. A game of the book opened from the Text tab, or from the book's PGN, and the same untouched one is shown again too. Untouched means nothing was changed in it since it came into the list: the same place in the book, the same side, the same moves, comments and tags. **New game** adds a blank one; **New game from this position** starts one at the move shown, keeping its diagram.
- Each game's menu, its buttons on the row under the pointer, or the keys of a focused row: **Rename…** (F2; the White, Black and Event tags, so the name is in the PGN, and the Site, Date and Round, in one undo step; a date is `YYYY.MM.DD` with `?` for each digit not known, `1992.??.??`, and Rename waits until it is one), **Duplicate**, **Move up / down** (Alt+↑ / Alt+↓), **Delete…** (Delete or Backspace; it asks first; deleting the last game leaves a blank one), and Enter shows it. A row can also be dragged to another place.
- **Several games.** Ctrl+click (⌘ on a Mac) adds a game to the selection or takes it out, Shift+click selects the games from the one last clicked; on a focused row, Shift+↑ / Shift+↓ selects on, Ctrl+A selects every game and Ctrl+Space picks the row. The game shown stays shown (in bold when it is not selected). The menu, buttons and keys of a selected row then act on all of them, as one step Undo takes back: **Delete…** (one question), **Duplicate** (a copy after each), **Move up / down** and dragging (together, in their order) and **Save PGN…** (the games selected, in list order). A plain click shows one game and selects it alone.
- **Undo** takes back a change to the list too (Ctrl+Z, the Edit menu or the rail's Undo, while Undo is on the chess side): whichever is newer, the list's last change or the last change to the game shown, goes first, and Undo names it (“Undo Delete game”). A deleted game comes back at its place with its own undo history. Games added are steps too: **New game**, **Duplicate**, **New game from this position**, **Open PGN…** (all the games of the file, one step), **Open as a new game** from Deleted moves, a diagram opened on the board (“Undo Load the diagram”, with the move number its page's moves gave it) and a game of the book opened from the Text tab (“Undo Open this game on the board”); Undo takes them out and shows the game shown before, and Redo puts them back. A game you changed after it was added is also kept in **Deleted moves** when Undo takes it out (the notice says so), so its changes are never lost; Redo takes it back out of there. Undoing **Open as a new game** puts the game back in Deleted moves. The list's undo history lasts for the session.
- **Open PGN…** adds every game of a file (at most 256). The file is read a line at a time: a line in UTF-8 as it is, any other as Windows-1252 (the Latin-1 the PGN standard names, with the quotes and dashes Windows adds), so a collection joined from files of both kinds keeps every accent, and a byte order mark at the start is left out; the notice says when a file was not all UTF-8. A game starts at the first tag after the moves of the one before; a bracket or a brace in a `;` comment or a `%` line is text and splits or merges nothing, and tags may share a line or be indented (one scanner decides this for every reader: Open PGN…, the PGN field, the book's PGN and the tools). In a tag's value only `\\` and `\"` are escapes, so `C:\games` is kept as written. The book's PGN is read the same way. **Save PGN…** writes the game shown, **Save all games as PGN…** (also the list's own button) the whole list in its order (a file you pick; a download on the web), in UTF-8; with **Write PGN files with a byte order mark (BOM)** in Preferences (off by default, remembered) the file starts with one, which some Windows programs need to read accents. Saving is refused for a document that does not allow copying. When some of the games being saved were read only up to a move that can't be played there (the rest of their text is a comment where the reading stopped, no longer moves), you are told first, each game named with the move it stopped at: **Save them as they are** or **Cancel**.
- **How PGN is written.** One writer writes every PGN PdfCraft makes (plan A9-F4): **Save PGN…**, **Save all games as PGN…**, **Copy PGN** (the clipboard too, decision D19), the autosave, the book's exports and the tools. The tags first (the seven of the roster, `SetUp` and `FEN` for a game that does not start from the standard position, then the others as read), then the moves in lines of at most 79 characters, broken only between words (a word longer than a line stands alone on its own), and never a line starting with `%`. A comment before a move goes right before it: after the `(` of a variation it starts, or after the variations of the move before. Two tags say what the moves say and follow them: `PlyCount` is written from the moves once the main line no longer has the length it had when the tag was read or set, and a read `ECO` is left out once the main line's first nine moves are no longer the ones it had (one changed, taken back or added) (the game keeps the tag; set it again to write it).

**Autosave.** Two seconds after the last change, when a document closes and on exit, each document's games are written to a file of their own in the `chess` folder of the recovery folder: `%LOCALAPPDATA%\PdfCraft\Recovery\chess` on Windows, `~/Library/Application Support/PdfCraft/Recovery/chess` on macOS, `~/.local/share/pdfcraft/recovery/chess` elsewhere (in portable mode, the portable data folder). The file is two lines of JSON: the document's keys (its `/ID`, path, and name and size), then the games: each one's PGN and what PGN cannot hold (the move shown, the board's side, an illegal position, the diagram it came from, where each move was printed, and every comment PGN would not give back as it is: each comment before a move, one with line breaks or double spaces, one longer than 4 KiB, a `[%…]` command). A save encodes again only the games changed since the last one (plan A9-I3a): 120 games with one changed take about a millisecond. Opening the document again finds them by its `/ID`, else by its path or its name and size (two different `/ID`s are two documents, and the `/ID` every extracted, split or combined PDF used to share counts as none), and saving the document takes the new keys at once.

- Files are written atomically, and only by the running instance that holds the recovery folder's lock; a file another running instance wrote is left alone, and you are told.
- A file a newer PdfCraft wrote (a higher format version) is never renamed or written over, whichever document it belongs to. Its own document's games are read as far as this version can make them out, and changes to them are not autosaved: you are told, and the list says “Saved by a newer PdfCraft: these games are only read here.” (**Save all games as PGN…** keeps them).
- Any other file that can't be read, or is too big, is renamed `….games.bad` (never deleted, never written over) and you are told; new games are saved from then on.
- Caps: 256 games and 32 MiB per document. Adding games past 256 is refused when you ask for it (**Open PGN…**, the PGN field's other games, **New game**, **Duplicate**, **New game from this position**, **Open as a new game**, a game of the book), and you are told how many were not added; untouched diagram games don't count. A list can still go past the caps: a diagram game changed, Undo of a delete, 32 MiB of comments. Its games are then not autosaved (you are told) until they are back under; nothing is ever evicted.
- **Quitting, closing a document and Close all ask** about games the autosave doesn't keep: over the caps, another window's, a newer PdfCraft's, or no lock or a write error. The question is “Chess games not saved”, asked one document after another, with **Save all games as PGN…** (quitting or closing stops there, so you can save them), **Quit without saving** (or **Close without saving**) and **Cancel**. Games left so, or all saved as PGN, aren't asked about again until they change. On the web nothing asks at quit; closing a document asks the same.
- **Protected documents:** an encrypted document's games are written only once you say so, in the one question about keeping its chess (asked once, with its corrections and book's PGN; plan A9-I1c); a document that doesn't allow copying never has its games written, and nothing is asked.
- On the web the games are kept in the browser's storage (4 MiB for all documents), written when the app saves its state; a value that can't be read is kept aside, and one a newer PdfCraft wrote is only read, never written over.

### The chess window

**Chess in its own window** (the rail's last tool, or the Board tab's menu) moves the board, with the Chess panel's Diagrams and Text tabs, into a window of its own, so the PDF can fill the main window, on another monitor if you like. From 760 pt wide the board sits beside the tabs; narrower, a **Board | Diagrams | Text** strip switches them. In the window the board can grow past the dock's 480 pt, up to 1,200 pt. Its keys are its own: the chess keys go to its rail and the app's shortcuts still work there. Closing it, or **Back to the main window**, puts the board back where it was: in its tab group, at its place in it, and in front only if it was in front when it left. **Back to the main window** in the Inspector does the same but leaves the Inspector in front (its Chess panel shows the Diagrams and Text again); if the board's group is gone, it goes at the end of the Inspector's group. Its size, place and tab are remembered in the settings (`docking_detached`). The size is what the window's contents get, the same whether the window is a separate one or drawn inside the main window, so going from one to the other keeps it. The place is kept in pixels of the desktop with the monitor it was on, so on monitors with different scaling the window comes back on its monitor (moved with it if that monitor moved); a window whose monitor is gone, or that would be mostly off every monitor, opens beside the main window instead, always wholly on a monitor. A value that isn't usable is ignored. `pdfcraft-cli ui --control FILE state` shows the window's geometry (`chess_window`: its place, the monitors and how it last showed), for checking it across monitors. If the window or its drawing surface can't be made, the board docks back once, with a notice, and no window is tried again in that session. Only on the desktop: on the web nothing offers it (a window remembered in the settings is drawn inside the page, with a Back to the main window button).

### Follow the source

A captured move, and a move of a game opened from the **Text** tab (a double-click on a move there, or **Open this game on the board**), remembers where it was printed. **Show in PDF** scrolls the page to the move shown and outlines it, unless it is on screen already. **Follow** (F, a switch for the session) does that whenever the move shown changes, so walking the game walks the book, with the board docked or in its own window. A move with no place on the page (played on the board, or typed) shows nothing.

### A worked example

The spec's scenario is a page of Grooten's *Chess Strategy for Club Players* (the game up to 17…Bc4 and the diagram under it, `2r2rk1/1p2ppb1/p2p1npp/q4P2/P1b1P2B/2NB4/1PP3PP/R3QR1K w - - 0 18`):

1. Double-click the diagram: game 1 of the document's collection, at move 18 (the number printed under the diagram), nothing renumbered.
2. Press X and select from `18.Nd5!` to `20.Raxe1`, prose included. In one capture, without the preview: the bold main line `18.Nd5! Qxe1 19.Nxe7+ Kh7 20.Raxe1`, the variation `18…Qd8 19.Bxf6! Bxf6 20.fxg6` with its sub-variation `(20.Nxf6+ exf6 21.Bxc4 Rxc4)` and the return `20…fxg6 21.Qg3 Kh7 22.e5!`, the prose as comments where it was, and `!` on 18.Nd5, 19.Bxf6 and 22.e5.
3. The next paragraph: `(20.Rfxe1)` inside the prose becomes a variation of 20.Raxe1, and the bold `20…Rc7 21.Bxc4 Rxc4` the main line. Captured alone first, the prose's `20…Rc7 21.e5!` extends the main line's end (with the preview); the bold line captured after it follows `20…Rc7`, puts `21.Bxc4` as the first reply and demotes `21.e5` to a variation (with the preview, because a move already there was demoted).
4. The forced modes build the same tree step by step from the empty game: as the line `18.Nd5! Qxe1`; as a variation `18…Qd8 19.Bxf6! Bxf6 20.fxg6`; as a sub-variation `20.Nxf6+`; as the line `20…exf6 21.Bxc4 Rxc4` (it continues the sub-variation); as the line `20…fxg6 21.Qg3`, which can't be played in the sub-variation (after 20.Nxf6+ Black is in check and no White piece is on g6), so it extends the outer variation, with the preview.
5. Click 20.Nxf6+, press C and select the prose after it: its comment. With **before** on the chip, the words before it become its comment-before (it starts a variation, so the PGN keeps it there).
6. Right-click 18…Qd8 ▸ **Promote one level**: it becomes the main line. ▸ **Demote**: back, identical, comment-before included. Ctrl+Z twice gives the same game, and the PDF was never touched.
7. The PGN reads back to itself. Close and reopen the app: the collection comes back, and the underline of captured text with it.
8. With **Follow** on, going to 20…exf6 scrolls the page to it and outlines it.
9. **Chess in its own window**: the board and the notation in a window of their own, the PDF in the whole main window. Closing it docks them back.

Steps 2–4 are tests of the engine (`engine::chess::capture`), of `chess_pgn_edit` and of the app; step 2 is one selection and no Enter, against about forty clicks on the board.

## Builds side by side

The chess edition is built into a `dist/app` folder, and earlier builds are kept beside it (`dist/app/anterior-…`). Each copy of PdfCraft in its own folder is its own instance: a PDF opened with an older build opens in that build, never in the current one's window (the single-instance socket's name carries a tag of the executable's folder). Every build says which it is: the short commit and the date the release script built (`PDFCRAFT_BUILD_ID`), or `dev`, in About, in `--version` (`pdfcraft 0.9.0, build 5f757af 2026-11-11`) and in `chess_status` (`build`, `version`). **Help ▸ Check for updates** asks nothing over the network: the original PdfCraft's releases lack the chess tools, so it says "PdfCraft Xadrez *build*: new versions come from the dist/app folder."

**Where the tools keep corrections and the books' PGNs** (plan A9-G5a). The command line and the MCP server keep them in the app's data folder (`chess/corrections`, `chess/reference`), as the app does, whatever the working folder; `store` and `reference_store` name another folder. With `--root` or the automation roots, that folder must be inside them: otherwise a reading tool reads none there and says `outside_root`, and a change is refused until `store` (or `reference_store`) names a folder inside them. `chess_store_migrate {from}` brings in what a `.pdfcraft` folder (or any folder of stores) keeps, merged and never copied over, the source only read; run again, it merges only what changed since (`migrated.json` records each file's size and time, by a hash of its folder and name, never its path).

`pdfcraft-cli chess scan FILE` prints the diagrams found. All paths are confined to `--root` (or to the automation read and write roots), and so are the default folders: `chess_pieces_import` needs `into` when files are confined, since its default is beside the executable. The files one call writes each need a name of their own, and none may be an open document's file or a file the call reads (the book's PGN, a saved cipher) unless the call says `overwrite: true`. A file the tools read is read up to its cap and no further (`cipher_in` 1 MiB, a PGN 32 MiB). With files confined, the replies name files relative to the root, and a file outside it by its name alone with `outside_root: true`.

The pages to OCR are chosen with `ocr`: `auto` (the default) reads only pages whose text layer is poor or missing, `off` reads none (a born-digital book), and `all` reads every page (a scanned book).

A scan that FineReader, Acrobat or Tesseract already recognised carries their text drawn invisibly over the page image. That layer reads cleanly but is a general OCR's guess at the figurines and annotation signs, so a page whose text is mostly invisible and whose images cover at least half of it is judged poor ("another program's OCR"), and `auto` reads it with chess OCR.

## How well it reads

All figures below are on the user's own models. Each has its command and the machine it ran on in the blueprint's log (§8).

- **Finding diagrams on a page image:** recall 0.9826 (113 of 115), precision 1.0, at 220 dpi on the prototype's field set.
- **Reading diagrams with the piece model:** 555 of 569 exact (0.9754) on the prototype's test split as it stood in October 2026. The target is 0.99.
  - 2026-11-11, the model retrained in ChessVisionOFF (`fccd0097`: 15,431 training boards of 19,370, synthetic square marks, `augx`), on the 2,027 test boards it never saw: 1,950 exact (0.962) against 1,875 (0.925) for the model it replaces (`a907f61`, 4,117 training boards; some of these boards may have been in its training, so its figure is if anything flattering). 87 boards only the new model reads right, 12 only the old. At the old gate of 0.80 the new model accepts 1,960 boards and 35 of them wrongly, the old 1,804 and 14; with its own gate of 0.95 it accepts 1,923, 26 wrongly. Of those 26, 16 are boards the old model reads into the very same wrong position, with near-certainty: label errors and orientation calls, more likely than piece errors.
  - On the 38-book bench (20 pages a book): diagrams accepted 875 → 973 of 1,097 at the new model's gate, almost all with the same position as before (the *Catastrophes & Tactics* volumes, read right but doubted, are now accepted whole); valid moves 25,658 → 25,543, because *Chess Tactics 4*'s boards, a style the new training lacks, are read otherwise (31 of 51 diagrams) and 136 of its moves no longer play. Six more books at 10 pages (Gallagher, Flores Rios, Capablanca, Koblenz, Reinfeld, Vladimirov): Capablanca's three diagrams go from garbage to two accepted endgames, Koblenz stays unread by either model, and two of Gallagher's ten go to review.
- **Chess OCR, fused with ocrs:** CER 0.88% and 98.0% of moves exact on the Caïssa benchmark (744 lines). These numbers are in-sample: the Dvoretsky lines are in the model's training data.
  - A scanned line of ten Helvetica moves is read 10 of 10.
  - Outline figurines in fonts the model never saw are still weak, at about 74% of moves for DejaVu Sans.
- Diagrams set in a chess diagram font are read exactly, from the text. A subset font whose codes were renumbered is read by its text map, and glyphs under 3 pt (stray spaces between the squares) are not squares.

**Speed and a real book** (2026-10-18, `pdfcraft-cli run` in release, the user's models, Windows 11 on an AMD desktop; *Dvoretsky's Endgame Manual* (2025), pages 51–60, one process per run, so nothing cached):

| Step | Time | Result |
|---|---|---|
| Find the diagrams | 0.31 s/page | 19 diagrams |
| Find and read them | 0.53 s/page | 19 of 19 accepted, all from the diagram font (before, by the piece model: the subset font's renumbered codes and its 0.7 pt spaces hid the boards; without the models no diagram was read and no move checked) |
| The recognised document (text layer) | 0.86 s/page | 459 moves, 18 games, 381 valid (7 before column order, 61 before subset figurines, 324 before games across diagrams, 369 before bracketed replies) |
| The recognised document with chess OCR | 1.8 s/page | |

That PDF's pages are set in two columns, and its figurines come from a subset font that renumbers its glyphs. Lines are cut at the gutter and read column by column, and a diagram's printed coordinates are left out (valid moves 7 → 61). A figurine is read from the text layer when its code names no piece, so the page is no longer judged poor and handed to OCR, whose words (`Taf7asch` for Tarrasch) replaced a clean layer (61 → 324). Games are found across diagrams: a text after two diagrams printed side by side starts from the one its first move is legal in, a diagram of a game's own position does not end it, and after an alternative written as prose a move is tried on the main line (324 → 369). Brackets after a move that hold the replies to it (`1.Kb1 (1...b3 2.Kb2; 1...a3 …)`) are played after it (369 → 381; with page 49, which holds page 50's diagram, 402 of 478). A diagram whose text gives the solution for each side to move (`Black, if on move, holds by 1...f5`, then `1.f5+`) starts a game for each: on pages 100–119, valid moves went from 790 to 812 of 978. Most of the rest are "not reached" after a move that cannot be played (often a position the prose describes but the book does not print), or belong to a diagram on a page that was not read.

### A game collection: Fischer's *My 60 Memorable Games* (Portuguese edition)

That book prints move numbers with no full stop (`19 ♖xd5`, Black's `15 … ♖xb6`), sets its game text larger than the introductions, and opens each game with a short introduction in a smaller italic. Numbers are now read without the full stop when a move follows; the body size is the book's, not the page's, so a page that opens a game does not make its moves and notes headings; a block with moves is never a heading; and a `1.` that the game from the last diagram cannot play starts the next game from the initial position. On pages 30–59, valid moves went from 142 to 468 of 1179 (and 63 false headings to 8 true ones), and the eight game titles and subtitles are the headings.

### A scanned book with an old OCR layer: Aagaard, *A Matter of Endgame Technique*

That PDF is a scan under an invisible text layer in Courier New, left by an earlier OCR program that read the figurines as stray symbols (`50.&xe5 ®f7 51.^d5`). Every move failed. Such words now make the layer poor (at least three on a page), so chess OCR reads the page again; the old layer's block sizes no longer decide headings on a page read with OCR; and a check written `†` (which OCR returns as a cross, `✝`) or mate `‡` after a move is read. On pages 40–49, with the models, valid moves went from 0 of 102 to 80 of 374. Moves OCR cuts with spaces (`♖ e 1`, `f1 =♕`) are put back together (80 → 87 of 376); the rest are mostly OCR misreadings.

### Two-column scans: Gallagher, *Winning With the King's Gambit*, and Flores Rios, *Chess Structures*

Both are scans with no text layer, read with chess OCR, set in two columns with game scores as tables (`2 f4 ef`). Two things kept the columns apart from being read in order. The OCR's glyph boxes are their ink (an `a` half an `h`), so against those heights every word gap looked like a gutter; the page text now gives each recognised glyph its line's height, as a text layer does. And a column whose score table is cut into narrow pieces fell below the average width a column needs; five wide lines now make it a column too. On pages 40–49 of Gallagher, valid moves went from 1 to 31 of 865; on pages 60–69 of Flores Rios, from 55 to 87 of 786 (Aagaard 87 → 85, the text-layer books unchanged). Both books draw their dark squares hatched, which the piece model misreads: their diagrams start no game until the model is trained on such boards.

### Headings on scanned pages: Pinski, *Italian Game and Evans Gambit*

A page read with chess OCR has no fonts to tell a heading by, so its headings come from what the page image shows. A frame drawn around a short text (Pinski's `Game 12` box) is a heading; so is a line set at least 1.4 times as tall as the body (a chapter's title). A box with a drop shadow, a thin outline with a thick edge offset on two sides (Pinski's `CHAPTER FOUR`), is a frame too, so the chapter number inside it is read instead of being taken for one large glyph.

A heading set in bold at the body's size (Pinski's `Summary`) is found by its strokes: each line, cut from the other column's text at the gutter, is measured on the page's ink (twice its ink over its edge pixels, the width of a stroke), and a line at least 1.35 times as wide as the body's strokes, with a blank line above it in its column and a line below it, is a heading when its words are mostly letters. Books set their main lines in bold, so the rule stays narrow: never the first or last line of a column, never a caption beside a board, never a line of moves. On the 38-book sample (2026-10-23) valid moves went from 25,221 to 25,247 with none lost, and the 7 new headings are all real: `CHAPTER FOUR` and `Summary` in both Pinski editions, and in *Amateur to IM* two section titles and the header `Sasikiran — Carlsen`, whose game is now played from move 1.

### Hatched and stippled boards

Old books print the dark squares hatched with lines (Euwe and Kramer, 1956; Gallagher) or stippled with dots (Reinfeld's *1001 Sacrificios y Combinaciones*, 1977). The piece model reads pieces on such squares about as well as on plain ones, but it reads an empty stippled square as a king, so none of Reinfeld's boards passed the gate.

A board the gate refuses whose dark squares are textured is now read once more with its **empty** dark squares painted one flat gray, the texture's average, and the second reading is kept only when the gate accepts it. A dark square counts as empty when each of its 4 × 4 blocks averages to the dark squares' usual gray: a block is wider than the hatch, and a piece pulls the blocks it covers towards white or black. Squares with a piece keep their texture: a hatch line is as thick as a piece's outline, so any filter that removes one removes the other.

### Boards cut to their squares

A contour can close on a diagram's frame, or on an outer border with the coordinates printed inside it (`a`–`h` under the board, `1`–`8` beside it, as Chernev's Capablanca prints them). The warp then takes along the frame, the paper between it and the squares, and the coordinates, and the 64 cells drift off the squares: a strip of letters becomes a rank, and on hatched boards the retry above no longer finds the empty dark squares, whose cells now hold paper or a neighbour (on the first Capablanca board it flattened a handful of them, and every one once the board was cut to its squares). The edge fit that trimmed double frames before cannot see this on hatched squares, where every square is all edges.

Each warped board is now also cut to the 8 × 8 grid that alternates most: each side of the grid moves, within 12 % of the crop, to where the difference between the two colours' squares, less the spread within each, is largest (on the board averaged down to 200 px, every second position, then every position near the best), and the cut is kept when it beats the whole crop by 0.05. No margin imitates the alternation, so the cut stops on the squares whatever is printed around them. It is not applied to an embedded image's box, which its own trims already cut to the grid. It costs about 20 ms a board with the edge fit.

### A puzzle book: Karpov, *Chess Combinations – World Champions 1*

The book prints six numbered diagrams a page (`№185. Teichmann – Em.Lasker` above each, which the text layer extracts as `N!!185.`) and the solutions 230 pages on (`№185. … 27 ... ♕e2+?`), on pages whose old OCR layer the chess OCR rereads (it reads `№` as `N9`). A caption above or below a diagram, in its column, that starts with a puzzle number gives the diagram that number (a caption with `№` wins over a bare `185.`, a caption goes to its nearest diagram, and a bare number needs a name after it). A paragraph of solutions that names a puzzle seen earlier closes the open game and plays its moves from that diagram; the game is tagged `PdfPuzzle`. On puzzle pages 40–41 and solution pages 275–276, valid moves went from 0 to 139 of 483, all twelve numbers read right; the other books unchanged.

Polgar's *Chess 5334 Problems, Combinations and Games* prints the number alone above each diagram (`1675`, the diagrams in the `skak` font, read exactly) and its solutions as the number alone before the key move (`1675 1.Rd3+`), 700 pages on. A caption that is the number alone counts (a section number such as `2.2 Combinations` does not), and a number alone just before a move numbered `1.` names a puzzle. For a number no diagram gave, the open game ends and the moves stay unchecked, instead of being read into whatever game was open. On pages 297–298 and 1009, 11 of the 12 key moves whose diagrams were read are valid (the twelfth, `1.O-O-O`, has no rook on its diagram), and no solution of an unread diagram is validated by chance.

A workbook may number each chapter's exercises from 1 and print all the solutions at the end. The numbered diagrams are kept by chapter: a new group starts where the numbering starts again, and it remembers the headings read before it. A solution whose number several chapters have goes to the chapter its label gives (`Ex. 6–12`), else to the one chapter that a heading over the solutions numbers (`Chapter 6`, `Solutions to Chapter IV`, `CAPÍTULO 7`) or names (the chapter's heading repeated), else by the chapters' order, since the solutions number again for each chapter. A label set beside the diagram it captions is not a solution. Nothing is guessed from the moves. None of the 38 sample books, read whole, has this layout, so this is proven by synthetic tests only. A bare number alone at the head or foot of a page is the page's number, not a caption, when it is as far from the page's index as the page numbers of the pages read before it: on the 38-book sample, 15 diagrams that the page number under them had numbered no longer are, and the valid moves are unchanged (24,423).

### Back to the main line after a prose digression

Annotated books leave the main line in prose (`2...Kd7? and gives away the h-pawn, White wins with 3.Kf4 Kd6 … 9.Kf5`) and come back to it in bold (`3.Kd4 Kf6!`). A numbered move like `3.Kd4` could also be an alternative inside the digression, to its own `3.Kf4`, and it used to be taken that way: the next move (`Kf6`, legal on the main line, not in the digression) then failed and stopped the line. Now a numbered move that is exactly the main line's next move, and legal there, goes back to the main line when the digression could only take it as an alternative to one of its own moves; a move that goes straight on from the digression (`1...c5 2.Nf3`) stays in it. On ten documents read earlier (Aagaard, Dvoretsky in two stretches, Fischer pt-BR, Flores Rios, Gallagher, Karpov, Polgar, Capablanca; replayed with `examples/walk_bench.rs`, no reading or OCR), valid moves went from 2,036 to 2,304 and moves not reached from 2,778 to 2,509; 13 moves got worse, in two games whose first chain of moves was itself a digression. Pages checked against the books: Fischer p. 46 (the Spielmann–Tartakover digression, then `7...♘c6 8.♗e3 ♘xd4?`), Flores Rios p. 60 (`If 14...♗xd6 15.♘xd6 …`, `Slightly better is 15...♕d7 …`), Dvoretsky p. 112.

### Moves in a sentence

A move without a number right after prose that ends with a preposition or a determiner (`to`, `on`, `at`, `the`, `of`, `from`, `into`, `for`, `a`, `any`, `our`, `this`, `against`…; not `with`, `via` or `by`, which introduce the moves a book plays) names a square, not a move: `…it does not come to d3`, `the knight is clearly on h5`. In a whole book a bare square so (`d3`, `h5`) is kept as text, unchecked, and the game goes on with the book's next numbered move; a move in bold still counts, and an idea printed `…d5` was already text. Measured by the Harikrishna book's own PGN (60 pages): the 12 such squares it does not have are no longer played, and every move it confirms stays. A piece's move after such a word (`Stops any ♘xf5`) is kept as text only when a selection is captured (the PGN toolbar): in whole books, a mention like that had sometimes stood in for a move the reading missed, and treating it as text lost more moves than it fixed. `walk_bench --reference` reports these moves by class, against the book's PGN.

### The main line by its printed weight

Annotated books print the main line in bold and their analysis in regular type (Dvoretsky, Fischer pt-BR). The text layer says which font each glyph is in, so each move now carries its weight (`bold` in the document's JSON, written only when true; documents read before have none). A page read with chess OCR takes it from its ink (see [Scans measured against born-digital books](#scans-measured-against-born-digital-books)). When the book's analysis comes first (`Black wins without any trouble after 1...Be6+ 2.Kg6 …`, then the game's **`1...Bxg7?`**) or goes straight on from the main line's last move (**`4...Kg4`** `Tarrasch had expected 5.Kf6? c4 …` **`5.Kg6!`**), the first chain read used to become the main line. Now, in a game with moves of both weights:

- a bold move after regular ones goes on from the last bold move, when it can be played there (an unnumbered one only after a bold move that was played: after one that failed it would be read a ply early);
- a bold move played on the bold line makes that line the main line, so the analysis stays as variations; one that could only be read inside the analysis does not;
- a game whose moves all have one weight is read as before.

On the same ten stretches read again on 2026-10-20 (release `pdfcraft-cli`, the user's models; Karpov and Capablanca are scans, used as stored) and replayed with `examples/walk_bench.rs` with and without the weights (`--plain`), valid moves went from 2,305 to 2,515 and moves not reached from 2,509 to 2,329: 217 better, 7 worse. Checked against the books: Dvoretsky p. 52 (`1...♗xg7? 2.♗xf5! ♔xf5 3.♔xg7 … 11.♔xa5 ♔xb3`, before the analysis `1...Be6+ 2.Kg6`), p. 51 (`1.♔c8!! b5 … 5.♔d4=` and `1.♔c3? b1=♕ … 4.♔xa4 ♔c3`, which had the analysis `1.c8=Q? …` and `1.Qc4+ Ka3` as main lines), pp. 100–101, 108–110 (the whole of Matanovic's rook ending, `1.♖d6+? … 22...♖c1`, after the book's detour into a pawn ending and its `Let's return to diagram 1-134`), 113, 115 and 119; Fischer pp. 37–38 (`6.♗e2 e5 … 11.♕e1`, past `6 h3` and `6 ♗c4`), 43–44, 47 and 52–54. Not real gains: on Fischer p. 49 (16 moves) the game started from the digression `19...♘e5`, because the centred diagram is ordered after the short line `19 … ♗xd5` beside it, and on p. 55 (14) from a diagram read with White to move; those moves are legal there by chance. The 7 worse moves were valid only on a branch that was already wrong (Fischer pp. 33 and 35, after `51...♔d6` and `57...c3` failed; p. 56, in the game started from the digression `26 b3`).

Tried and not kept: guessing a different move in place of a failed one when the next printed moves fit exactly one move like it. All six moves it would have changed were printed correctly; each had failed because of something earlier (the line on the wrong branch, a short capture such as `hg` not read as a move), so guessing only hides the cause.

### A diagram centred above a short line

Fischer's *My 60 Memorable Games* centres each diagram (its caption printed beside it, `Position after 19 ♘d5!`) and sets the next move under it at the left margin (`19 … ♗xd5`), so the move lies wholly to the left of the diagram. A diagram used to go only before a line under it or in a column to its right, so it came after that move: the game was played on from a position before its last move, closed, and the book's analysis became a new game. A diagram now also goes before a line wholly below it on its side of the gutter, or of the page's middle on a page without one; a diagram or line across that middle is on both sides. On a two-column page, a left-column line below a right-column diagram is still read first. On the ten re-read stretches, valid moves went from 2,515 to 2,948 (all in Fischer pp. 30–59: 706 → 1,139 of 1,179; not reached 414 → 20; 18 games → 9), no move got worse, and the other nine stretches read exactly as before. Pages checked against the book: Fischer pp. 30, 31, 33, 34, 38, 47, 52, 56.

### A magazine's running head

*Chess Evolution* 2013 (a weekly magazine, collected by year) sets `Issue 45` as a heading atop every page of an issue. Every heading ended the game, so each annotated game stopped at each page break, and the moves of the next page waited for a diagram to start from, even one printed inside a variation. Now a heading that one of the two pages before set in the same words at the same height (top and bottom within half its height) is a running head: it stays a heading in the document but ends no game and names no chapter or solution. On the issue's first page there is no page before it, so the head still starts a section there. The same words set lower on the page, or the next issue's head, still end the game. On two stretches of about 30 pages each (pages 1–29 and 700–730, 2,354 moves, read with `ocr: off` and replayed with `walk_bench`), valid moves went from 1,529 to 1,976 and unchecked ones from 533 to 0; two moves were lost on page 724, where the book itself prints `19...20.Ne2`. The 38-book sample does not change, move for move (25,571).

### The rest of the magazine: page numbers, hyphens, smileys, diagrams in variations, headers

Five more things the same magazine showed, each read now as the page means it:

- **Page numbers.** A paragraph of a bare number (at most four digits) with no block above it or none below it is the page's printed number. It stays in the document, but the walker passes over it as over a running head: it was a comment in the game the page break cut (`{10 11}`).
- **Hyphens.** A document's paragraphs join a word a hyphen cut at a line's end (`cal-` `culation`), as a selection's fragment already did, in the text and in the games' comments. So do two paragraphs one after the other, a column's foot and the next column's head (`cor-` `rect`), and a paragraph left empty goes. A square, a digit or a sign before the hyphen is never joined (`d4-` `d5`), and after one letter alone the hyphen stays (`e-file`).
- **Smileys.** `:)`, `;)`, `:(` and their forms with a nose, standing as a word of their own, are prose: their bracket opens or closes no variation and their `;` separates none (`it usually works! :)` had closed a `[ ]` variation). A `;` standing alone between a variation's siblings is no longer a comment (`{;}`).
- **A diagram inside a variation.** A diagram that comes while a game is open keeps the game when it shows the position any open line reached, not only the main line. The innermost such line goes on and the lines inside it close, unflagged. Chess Evolution sets diagrams in its `[ ]` analysis after the move they show; the moves after one went to a new game from the diagram, or onto the main line.
- **The game's header.** ChessBase prints `(1) Vachier-Lagrave,Maxime (2711) — Grigoryan,Karen H (2513) [C02]` and, under it, `Al Ain Classic 2012 Al-Ain UAE (5.3), 26.12.2012 [Balogh Csaba]`, with the spaces around the dash and before the brackets coming and going (`Iturrizaga, E(2653)-Nakamura, H(2775)`, `Greek league,` with no date). The header ends the open game, whose comments no longer take the players' names, and the next game to start fills White, Black, Event, Round, Date (`1967.??.??` for a year), WhiteElo, BlackElo, ECO and Annotator from it (`doc::header`). The players' line needs its game number in brackets, so a heading such as `A. Smith — B. Jones` is read as before. The solutions pages set a header over each diagram in two columns, and the page is read across them. So a header waits for the next game to start in its own column, on its page or the next, and keeps the other diagrams waiting; it drops only a diagram that came while the closed game was open and no move settled. A newer header in a column takes the place of one whose game never started, and a game with no header in its column takes the single header waiting (one at a column's foot, its moves atop the next).

Measured on 2026-10-29 with `walk_bench` on the four samples (pages 1–30 and about 700–730 of each year, 4,889 moves), valid moves went from 3,927 to 4,156, with 256 gained and 27 lost; 19 of the gained come from headers ending games, which lost none. The losses are in endgame analysis whose nested lines now read differently. Read again live (`pdfcraft-cli`, `ocr: off`), the samples give 4,158. 62 of the 93 games read have their players and event; the ones checked by hand (2013 pp. 1–29, 2014 pp. 1–30 and 749–778) each sit under their own header. On the 38-book sample, valid moves went from 25,571 to 25,656 (125 gained in four books, 40 lost). 39 of the losses are in one book whose section labels (`(1a3)`, `(1b1)`) and a lost bracket before `32.Nd3` had sent a variation to a new game by luck; a header, a smiley, a page number and a label in brackets changed nothing there. The hyphens are joined when the page is read, not when it is walked, so `walk_bench` does not see them; read again live, the cut words in the 2013 samples' comments went from 114 to 46 with the line join and to 1 with the paragraph join (`the game- which`, a dash the book sets so).

Still open on this magazine: a bare move in prose (`the same Rh7 doesn't work`) is played; a move glued to the words after it (`59...♕e4+AllinallwesawanicepositionalwinbyBlack`) is read as text; and a result written with an en dash (`0–1`) does not end a game in a book (only fragments read the extended results).

### Three or more columns, a diagram on one side, and a page read alone

Three changes to where things go on a page, and one to a page read on its own:

- **Columns.** A page's gutter is looked for again among the lines on each side of it (the same rule: 30–70% of that side, few lines across, columns as wide as on the whole page), up to four columns. Each band between lines across a gutter is read down each side in turn, and a line across only some of the columns (a title over the two right ones) cuts only those. A diagram is in every column it spans.
- **One side of a one-column page.** On a page with no gutter where at least half of the lines cross the middle (one column of text), a line wholly below a diagram comes after it on either side of the middle, unless it lies under another board in its own column (a row of boards, each with its caption). A page of short lines with no gutter may be two columns too short to find one, and keeps the sides apart as before.
- **A page read alone.** The Text tab reads one page; a game opened from it reads the pages around it one at a time. The caption at the foot of the page before (`Exercício 7`, whose board is at the top of the next page) used to be lost. Now the page before is looked at, not read: its text layer and where its diagrams are, not what they hold; and a page walked again after the page before it takes that page's foot caption, which the document's JSON keeps as `trailing`.

Measured on 2026-10-24 (release `pdfcraft-cli`, the user's models). On the 38-book sample (20 pages of each, read together) valid moves stayed at 25,247 (10,601 from a diagram), none gained or lost, and no page's blocks changed order: none of those 760 pages has three columns, or a diagram on one side of a one-column page with a line below it on the other side, and no window's first page has a caption at the foot of the page before it. Across the text layers of the 38 whole books, the only pages found with three columns are one book's index of games (two pages, a table of White, Black, event and page), read column by column before (as two) and after (as three), with no moves in it; the scanned books were not searched beyond their samples. Read a page at a time, as the Text tab reads them, the samples of the four books that caption a diagram at the foot of the page before it number 41 diagrams instead of 33 (12, 8, 12 and 9: the very numbers the 20 pages read together give), with the same valid moves (their solutions are on pages outside the samples). The ten stored documents replayed with `examples/walk_bench.rs` read exactly as before (2,319 valid moves): their JSON has no `trailing`.

### Scans measured against born-digital books

A born-digital book is its own answer key: its text layer is exact, and the same pages rendered and read with chess OCR (`chess_document` with `ocr: all`) show what a scan of it would lose, move by move. On six pages of Ulf Andersson's *Ulf the Attacker* (two columns, figurine notation, the main line in bold), OCR gave 144 valid moves against the text layer's 257. The glyphs themselves were nearly all right (268 of 278 moves and 31 of 32 annotation signs read the same); what was lost was put together after them:

- **Lines across columns.** The glyph reader banded the whole page, and the two columns' baselines are 18 px apart at 300 dpi, so dots, ellipses and figurines went to the other column's lines (`4...♘f6` came out as `4...`, `♘` and `f6`). A page's columns are now found by their gutters (a run of pixel columns at least 1.5 text scales wide over which the text stands at most 3 scales tall, with 40 text boxes on each side) and broken one by one; a line's baseline is the median bottom of its tall boxes, so a descender does not move it. Where most lines share a baseline with the other column's (a page set on one grid, a table), the page is broken across as before, since there the other column's lines steady the bands: a speck over a line beside a frame (Pinski p. 49) would otherwise cut the line in two.
- **Weight.** A word whose letters and digits (not its figurines, which an outline font draws thin in a bold line too, nor a lone glyph) have strokes at least 1.2 times the page's body is bold, and its runs are marked bold as a bold font marks them in a text layer, so the walker keeps the main line. Short bold moves (`♗g7`) measured 1.25–1.3 times the body, regular words at most 1.15; 133 of the 135 bold moves were found, and no regular one.
- **A header box ruled in light gray** (a 146 border on white, a 242 fill) is a frame: frames are looked for halfway between the text's threshold and the paper, so the game's header is a heading again.
- **Misreadings:** `(1 7...` joins into `(17...`; `19.0.0` (the dash read as a full stop) is castling; a narrow `1` closes up to the next figure inside a number (`Game 1 8`, `1 970`) but not after a square's file (`♖d1 0-0`); the x-height is measured on `a e m n r`, so a capital among ascenders stays one (`as white` misled the side-to-move words); an `X` between a file or figurine and a square is the capture's `x` and a `C` between a piece and a rank the file `c` (an `x` with a speck over it stands as tall as a capital); and a wide letter is never cut into a letter and an opening bracket (`who` read `M(ho` opened a variation that swallowed the next page's moves).

With all of it the six pages read 258 valid moves by OCR. On the 38 books (`cargo xtask chess-bench`, 20 pages each) valid moves went from 25,435 to 25,570 (+165 −30: about 9 of the 30 are castling now written `0-0` where it read `o-o`, and most others moved within pages that gained more; Pinski 2nd ed. p. 42 lost 3 to a weight the walker took as the main line). The OCR ground truth: CER 1.24% → 1.05%, moves unchanged.

### The text between a diagram and its move

What a book prints between a diagram and the move that settles it is the game's. When the game goes on past the diagram (a diagram reprinting its position, or the main line's next move), the words are the comment where they stand, and a bracket among them closes the variation the diagram was set in, so the main line's next move is played on the main line, not inside that variation; a result among them ends the game. When a game starts from the diagram, they are its first comment, in the PGN (the one written without the book's PGN) and on the board, less the cue of a "position after" caption whose move was read (`Position after:` in `A sharp line. Position after: 2...Nc6`). Only when no game takes the diagram do they go to none. They are kept up to a comment's 64 KiB, and the game is flagged past that. Text printed after a move's variations is the next move's comment before (`1.e4 {A} (1.d4 d5) {B} 1...e5`), in the document's PGN and on the board; the board's own PGN still writes it before the variations (plan A9, F4).

Measured on 2026-11-12 by walking again four documents read before (100 pages of Dvoretsky, 30 of a Fischer collection, Flores Rios, 60 pages of *Chess Evolution*): every passage of four words or more printed after a diagram is in its game's comments now (6 in games that go on past the diagram, 1,659 characters, and 33 before the first move of a game from the diagram, 3,813 characters, were in none before; a game's players' line among them was already its tags), and no move changed status. On the chess gate's documents, `walk_bench` gained 24 valid moves and lost none: two of Carsten Hansen's books open a variation with a bracket just after a diagram (`How should White best continue? (11...♗b7 is more solid) 12.♘f3`, and a page that starts `(Black should have played 12...Re8`), which was dropped, so the variation never opened and the moves after it were not reached.

### What each block of a page is

A page's text blocks say what they are to the book, decided from the page alone: the book's text, the page's printed number (a bare number at its head or foot), a game's header (the players' line and the event's under it) or a diagram's own text. The lines whose centre lies inside a diagram's box are that diagram's text, a paragraph never joined with the lines outside it, whatever their font or the layout's hint: a diagram set in a font the catalogue does not know (a publisher's own, or one renamed in its `name` table) used to leave its glyphs as a heading (`4*+*+p+*+5`), which ended the game and left the diagram's moves with no position. The walk passes over the page's number, a header's event line and a diagram's text; the header still gives the next game its tags. The document's JSON says it as `"role"` on the block (`"folio"`, `"game_header"`, `"diagram_text"`; nothing for the book's text), so an earlier build reads them as plain blocks, and a document written before is given its page's roles when its moves are walked again. The exports leave the page's furniture out (plan A9-L1b): HTML, EPUB and its contents, Word, RTF, Markdown and the PGN written with the book's PGN write neither the page's printed number, nor a diagram's own text, nor a running head (a running head is no role, since it needs the pages before it: the walk writes the page's running heads beside it, `running_heads` in the JSON, and walking the page again writes them afresh). A game's header stays, the book's own words. *Chess Evolution*'s `Issue 47`, ten entries of an issue's EPUB contents and ten `##` of its Markdown, is now one, where the issue starts. A book whose PDF says no page labels is paged in its EPUB by the numbers it prints: each page whose printed number is as far from its place as most pages' are takes it, a page between two such pages that prints none (a chapter's first page) takes the number its place gives, and the page list and the diagrams say `15` where they said `1`. The other exports still say the page's own number.

### Paragraphs by their geometry

The page's layout gives hints (a heading here, a paragraph there), and they cut paragraphs where a line's type or weight changes, often mid-sentence (`…even nicer to have a` | `knight on f4, hitting…`, 4 points apart). The hint now says only what a line is, a heading's or a paragraph's; whether a paragraph goes on is the geometry's: lines that stand close in one column (a gap of at most 0.8 of a line) are one paragraph across two of the layout's hints where the sentence goes on (the line before ends in a word or a comma, or the next starts in a small letter), and lines a blank line apart are two even within one hint. A heading's lines are its hint's, as before. On 60 pages of Harikrishna's *Beat the French Defense with 3.Nc3*, paragraphs cut mid-sentence went from 105 of 619 to 2 of 495 (both at a column's foot); on 60 pages of *Chess Evolution* 2013, from 203 of 993 to 4 of 694. Of the 416 boundaries joined there, one is at a sentence's end. A word a hyphen cut at a line's end is still always joined (`well-` `known` gives `wellknown`, plan A9, A2-15).

### Every change said, and the marks checked

- **A misreading read again is said.** The reader reads again, on every page, the characters an old OCR layer sets for others in notation (`l` for `1`: `6.Rel` is `Re1`; `S` for `5` or `8`; a full stop inside a square; bullets for dots). A born-digital book can carry such a layer too, so the move says it was read again, with what was printed (a review flag, "Rel → Re1"); a move number read again (`2S.`) says it on the move after it. Joining a move a scan cut at a space (`♖ e1`) is no misreading and says nothing.
- **Marks that do not fit.** A move played whose printed marks the position does not bear out is flagged: a capture mark on a move that takes nothing (`Nxf3` to an empty square), a check mark on one that gives no check, a mate mark on one that does not mate. Many books print no check, so a mark left out is no sign. Such a move is weak evidence: it settles no choice of diagram (a first move that fits the diagram before it only with a wrong capture mark, and another diagram nearby cleanly, starts from that one).

### The book's language

An export is in the language of the book's text, not of its piece letters: a book printed with figurines says nothing in its letters, so a Brazilian book used to come out as English (`<html lang="en">`, `dc:language` `en`, Word spell-checking in English, "Diagram 1, page 1: White to move"). The book's language is its PDF's `/Lang` when it gives one, else the language whose function words (articles, conjunctions, prepositions: `the`, `and`, `of`; `o`, `com`, `não`; `der`, `und`…) its prose holds most, over every page read; when neither says, the piece letters' as before. Each page of the document says it as `text_lang`, a checked language tag (`pt-BR`), beside `lang`, its piece letters'; a diagram is described in it, and `chess_document` and the exports say it as `text_lang`.

### What a diagram shows, and what was printed

A diagram's reading is what was printed, as read: its position, where its side to move came from (said on the page, a "position after" caption, the first move's number, the position itself, or assumed), the side the board is printed from, and the gate's verdict. Nothing rewrites it. What the text around it settles (a caption `Position after: 5.dxc5` makes it Black to move at 5; the first move `23...` makes it Black to move at 23; `1.e4` under a diagram whose side was only assumed says White) is kept beside it, and so is the position the book's PGN confirms. A diagram shows, all told, the PGN's position, else the one the text settled, else the one read (a position you set is yours); that position is the one an export draws, writes as FEN, describes and links to lichess (from the side the board is printed from). A side only assumed is said not given (**Diagram 1, page 17: side to move not given**), never **White to move**. Taking the book's PGN away leaves the reading as it was, so linking again starts from it.

### Caps, labels, signs and descriptive notation

A document holds 20,000 games (it held 4,096: a book of exercises such as the Polgár would have lost its last 1,200 solutions, unsaid). Past them no game starts: the first page where one would says so in its notes (and its flag, `too_many_games`), and its moves stay in the text, unchecked. Lines numbered with capitals (`A)`, `B2)`, `B2.1)`, also in brackets: `(A)`, `(B2)`) separate sibling variations as `a)` and `(a)` do; their `)` used to close the variation they stood in. Words in square brackets with no move in them go back to the comment in square brackets (`[brackets]` was written `(brackets)`), and a row of three or more `=`, `-` or `*` is a word, not three assessments (`=====` was read `$144 $144 $10`). A font named after a city (`ZurichBT`, `Berlin Sans`) is a chess font only with a chess word in its name too (`ZurichDG`, `BerlinChess`): Bitstream's Zurich, a text face, was taken for one. A page printed in descriptive notation (`P-K4`, `N-KB3`, `PxP`; Spanish and Portuguese `P4R`, `C3AR`) says so in its notes, **descriptive notation (P-K4, P-K4, N-KB3): not supported; its moves were not read**, and in its flag (`descriptive_notation`): such a book gave no game and said nothing. Converting it to algebraic is not done (decision D27).

The pages read are always in the book's order, each once (`PageSet`, plan A9-G7b): the tools' `pages` (`[2, 1]`, `[1, 1]`), the interface and the exports all read through it, so pages given out of order no longer read a game backwards, nor does a page given twice double its games and its HTML's ids. A game goes on from one page only onto the next: pages read with a gap between them (`pages: [3, 7]`) start the later one with no game open and no diagram waiting.

### Reading a selection (fragment mode)

The PGN toolbar captures a selection on the page into the game on the board (its spec, `plan/chess/pgn-toolbar.md`, step T2a for the reader; the capture in the app is steps T3 and T7a, see [Capturing text](#capturing-text) under the [PGN toolbar](#pgn-toolbar)). The reader is the same game walker that reads whole books, in a *fragment mode* (`chessvision::doc::fragment`): it starts from the position it is given (never renumbered from the moves), reads one game (a `1.e4` quoted in prose does not start another, and a move numbered before the start position is prose), and writes the game out as the items `Game::graft` takes, moves with their printed half-move, weight and box. The selection is read in the document's language, never one guessed from a few words (`Rc7` is a rook in English and a king in Portuguese). Rules added for it:

- a bracket lost in the text is assumed when a numbered move fits only outside the variation (flagged);
- a move without a number after prose words stays in the comment (`the break …f5`), unless it is bold;
- inside brackets, `;` before a numbered move and labels `a)`, `(b)` separate sibling variations, and a label is never a closing bracket;
- `1:0`, `1–0` and `(1-0)` end the selection as `1-0` does; what follows is left over, never dropped;
- `20.…`, `20. …Qd8` and `…Qd8` are notation, and a move after a lone ellipsis is Black's;
- a word cut by a hyphen at a line's end is joined only between letters (`posi-` `tion`), never after a square or a digit (`Nd7-` `b6`, `1-` `0`).

Whole books take only the rules that made no move worse on the ten stored documents (`examples/walk_bench.rs --rules=`): the assumed bracket, the separators and the ellipsis, 2,304 → 2,327 valid moves, 23 better and none worse. Moves in prose made 88 worse (books go on after prose without numbers) and the new results 3 (moves that were played into the wrong game before a `0:1` ended the right one), so those stay for selections. Reading every variation the walker built again as a selection, from the position before it, and grafting it (`examples/fragment_bench.rs`) gives the walker's own tree for 100% of Dvoretsky's (59 of 59), 94.1% of the second Dvoretsky stretch, 91.0% of Fischer's (81 of 89) and 94.2% overall (275 of 292). Most of the differences are the whole-book reading's: a numbered move after a prose digression goes back to the variation's own line in the selection, while the whole book keeps it in the digression.

## Limits

- **Moves and text**
  - A line stops at a move that cannot be played (a misprint, a misread diagram, or a line read onto the wrong branch): its later moves are "not reached" until a numbered move finds its place again. On a page read from its picture (by chess OCR, or under an earlier OCR's invisible layer), such a move is first read with `c` and `e` swapped in one of its files, since a scan loses the bar of an `e` (`cxf4` for `exf4`): when exactly one such reading is legal it is played, and the move is flagged for review with what was printed. A book's own text layer is never read so. A bracket between two small letters is read as part of the word, not as a variation's: an OCR's broken `o` or `e` (`m(nre` for `move`) or a word's optional ending (`move(s)`). A game whose first chain of moves is a digression (the book's analysis of an earlier move printed before the game goes on) has that digression as its main line when the book does not set its main line in bold, or the page is a scan. A diagram centred beside a short line of moves can be read after that line, so a game can start from the analysis that follows it. A game whose diagram is on a page that was not read has no position.
  - More than four columns are read as four at most. A table set in columns (a book's index of games) is read column by column like text.
  - A diagram goes among the lines by its place on the page: before the first line under its middle, in a column to its right, or wholly below it in a column it shares (on a page of one column, on either side of the middle). On a page of short lines with no gutter, a diagram set entirely on one side of the middle still comes after a line below it on the other side.
  - Umlauts in prose come through only where the glyph reader has them, because ocrs reads ASCII only.
  - On a scanned page, a heading set only in bold at the body's size is read as a paragraph at the top of a column, under a board or without a blank line above it; one inside an annotated game ends the game, as every heading does but a running head. Display type drawn as thin outlines would be taken for frames.
  - A solution finds its chapter's exercise only from the chapter its label gives, a heading over it that numbers the chapter or repeats its heading word for word, or the chapters' order; a chapter with no solutions shifts that order. The page number of the first page read, with no page before it, can still number a diagram at the foot of that page. A page read alone takes the caption at the foot of the page before from that page's text layer only: on a scan, where only chess OCR would read it, it is lost.
- **Readings and corrections**
  - A reading the decoder repaired is never linked or accepted until a person confirms it.
  - The book's cipher (what a figurine font or a misreading maps to) is carried from page to page and between reads while the document is open, each open document its own: reading another book in between leaves it as it was. Headless runs save and load it with `cipher_out` / `cipher_in`. It is not saved inside the PDF.
- **PGN toolbar**
  - A PGN file keeps a comment before a move only where the move starts a variation or comes after the variations of the move before; elsewhere it joins the comment after the move before (the app's autosave keeps it apart).
  - Drawing commands typed into a move's comment become drawings. Typed into the comment before a move, they stay text there, unless the move continues its line with no variation before it: the PGN then writes that comment with the one after the move before, and reading it back draws them on that move. `chess_pgn_edit` edits one game of a PGN at a time: `game` picks it (0-based, the first by default) and the reply says how many the PGN holds.
  - The game's undo history, and the list's, are not kept across sessions. The lines the engine found for a position are kept for the session only.
  - `chess_games` works on PGN text and files: it cannot reach the games the app autosaved for a document.
  - The chess window has not yet been checked on the real executable across two monitors with different scaling (the rules are tested with this machine's 1920 × 1080 at 100% and 3440 × 1440 at 150%). Monitors are known only on the desktop; on the web, and where they can't be read, a window opens inside the main window. A window placed on a monitor of another scale is moved there once after it opens. A place saved before 2026-10-21 (U5) is not used: the window opens beside the main window once.
- **Speed:** reading a page with OCR, exporting a whole book and aligning it to its PGN run off the interface thread. Export and **Align the book to the PGN** say which page they are on, with a bar, and × (**Stop**) stops them: nothing is written, and the book's link stays as it was. A page read can't be stopped, but asking for another takes its place, and it never waits for an export or an alignment. On the web, **Detect diagrams** runs a page at a time, about 50 ms a frame, with its progress and × as on the desktop; Export and Align the book still run inside one frame there, so the web does them only for a book of at most 20 pages, and says why otherwise.
